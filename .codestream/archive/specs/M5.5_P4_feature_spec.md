# FEATURE SPECIFICATION: M5.5_P4 — One full-width clickable row, one contextual Delete

## Phase Summary

This phase closes **BUG-006** (inline Edit/Delete icons on list items; row click should open edit mode; Delete belongs in the contextual `TopBar` with a confirmation dialog) and **BUG-007** (`PageContainer`'s `max-w-7xl` pillar; card/tile grids should become full-width dense list rows) in a single vertical slice, presentation-layer only.

The two bugs are **not** two independent diffs. BUG-006 removes the per-row action cluster; BUG-007 removes the tile shape. What remains after both is one thing: **a full-width, dense, directly-clickable list row with its content on the left and no action cluster on the right.** This phase therefore introduces **one shared row primitive** (`ListRow`) used by all four entity families rather than editing four card layouts in parallel, and **one shared confirmation dialog** (`ConfirmDialog`) used by all four Delete flows rather than four `window.confirm` calls.

Nothing about *what* gets deleted, *which endpoint* is called, or *which callback* fires changes. `deleteRecipe`, `deleteEquipmentProfile`, `deleteMashProfile`, `deleteFermentationProfile` in `apps/web/src/api/client.ts` are called from the same owning components, with the same arguments, and the same `onDeleted(id)` callbacks fire on success. Only the **UI trigger location** (row → contextual TopBar) and the **confirmation surface** (`window.confirm` → `ConfirmDialog`) move.

### Key Behaviors

1. **Full-width layout.** `PAGE_CONTAINER_CLASS` drops `mx-auto` and `max-w-7xl`. Every route that already renders `<PageContainer>` becomes full-width responsive with unchanged horizontal padding and vertical rhythm. No call site changes; no variant prop is introduced (the constant remains a single frozen value — see Resolved Ambiguity 1).
2. **One dense row primitive.** A new `ListRow` renders a full-width, edge-to-edge row inside a new `LIST_CONTAINER_CLASS` wrapper. Recipe Library's 3-column card grid and the three profile managers' stacked rounded cards are all replaced by it.
3. **Row click opens edit mode.** Activating a row (click, `Enter`, or `Space`) invokes the same handler the removed pencil/name button invoked: `handleOpen(id)` for recipes, `setFormTarget({ mode: 'edit', profile })` for the three profile managers.
4. **No inline Edit or Delete icons remain.** The `Pencil` and `Trash2` buttons are removed from all four list surfaces. The `Pencil` icon in `RecipeLibrary` was an *inline rename* control, not an edit-mode entry; its capability is preserved because the recipe editor already owns an editable name input (`App.tsx:485-486`) which the row click now reaches directly.
5. **Delete is a contextual TopBar action in edit mode.** In each profile form's `edit` mode, a `Delete` button renders in `TopBar`'s existing `children` (actions) slot, left of `Cancel` and `Save Profile`. In the recipe editor route, a `Delete` button renders in `App.tsx`'s editor `TopBar`, left of `Scale Batch`. Create mode never shows Delete.
6. **Confirmation before deletion, list view on success.** Delete opens `ConfirmDialog`; confirming issues the existing API call; on success the view returns to the owning list; on failure the form/editor stays open and shows the error.

### Resolved Ambiguities (Binding)

1. **This phase deliberately supersedes M5.5_P3's `PAGE_CONTAINER_CLASS` decision.** P3 froze the constant at `'mx-auto w-full max-w-7xl px-4 sm:px-6 lg:px-8 py-6'` and deliberately refused a width variant (P3 deviation 2), reasoning that a second width is the exact mechanism that produced BUG-005. **That reasoning is retained; only the value changes.** BUG-007 revises the frozen value, it does not unfreeze the constant. The new value is exactly `'w-full px-4 sm:px-6 lg:px-8 py-6'` — `mx-auto` and `max-w-7xl` removed, the four padding tokens and `py-6` byte-identical to P3's. This is **not** a conflict with P3 to be adjudicated; it is P4's explicit, disclosed revision of a P3 constant, recorded as deviation register entry 6. Adding a `variant` prop, a second exported class, or any conditional width is **forbidden** by this spec.
2. **"The row" vs. nested interactive elements.** The clickable region is the `ListRow` root element in its entirety, including its padding and every non-interactive descendant (name, meta line, badges). A descendant that is itself an interactive control (the retained Duplicate button in `RecipeLibrary`) **must** call `event.stopPropagation()` in its own `onClick` so that activating it does **not** also open edit mode. The row root is a `<div role="button" tabIndex={0}>`, **not** a `<button>`, precisely so a nested `<button>` remains valid HTML.
3. **Keyboard activation is exactly `Enter` and `Space`.** `onKeyDown` fires the row's open handler when `event.key === 'Enter'` or `event.key === ' '` **and** `event.target === event.currentTarget` (so a keypress inside a nested control never bubbles into opening the row). `Space` additionally calls `event.preventDefault()` to suppress page scroll. No other key activates the row.
4. **`RecipeLibrary`'s Duplicate action is RETAINED, not removed.** BUG-006 names only Edit and Delete. Removing Duplicate would delete a capability with no other entry point in the app (`duplicateRecipe` is called from nowhere else). It survives as the row's single `trailing` control, keeps its `Copy` icon and `title="Duplicate"`, and takes the `stopPropagation` rule of Ambiguity 2. Recorded as deviation register entry 1.
5. **`RecipeLibrary`'s inline rename is REMOVED (pencil + `patchRecipeName` call site).** This is the `Pencil` button BUG-006 names. Its capability is not lost: the row click opens the recipe editor, whose name input is the canonical rename surface. `patchRecipeName` **remains exported from `api/client.ts` and is not deleted** — only this one call site goes away. `renamingId` / `renameValue` state and `startRename` / `commitRename` are removed as now-dead code (see §2.8's legacy-cleanup list). Recorded as deviation register entry 2.
6. **Delete-blocked ("in use") semantics are preserved, relocated.** Today each profile manager disables a row's Delete when `profile.id === activeRecipeEquipmentId` / `activeRecipeProfileId` and shows an amber in-row note. That rule now lives on the form's TopBar Delete button: `disabled` when `deleteAction.blockedReason !== null`, with `title={blockedReason}`. The blocked reason string is unchanged: `'In use by the recipe currently open in the editor'`. The amber in-row note is removed with the row's action cluster.
7. **The API call stays where it is today.** For the three profile families the `delete*Profile(...)` call, the `deletingId`/busy state and the `deleteError` state remain in the **manager** (`EquipmentManager` / `MashProfileManager` / `FermentationProfileManager`), unchanged in body except for the removal of `window.confirm`. The form receives them as a `deleteAction` prop object and renders the button, dialog, and error. For recipes the `deleteRecipe` call moves from `RecipeLibrary` to `App.tsx`, because the recipe's "edit mode" **is** the `editor` route, which `App.tsx` owns. No delete logic moves into `api/client.ts`, and no endpoint, method, path, or argument shape changes anywhere.
8. **`window.confirm` is replaced by `ConfirmDialog` for these four delete flows only.** The unrelated unsaved-changes `window.confirm` in `App.tsx`'s `confirmLeaveEditorIfDirty` (line 105) is **untouched** — it is a different concern (M5.5_P2 deviation 1 deliberately left it alone) and converting it is out of scope.
9. **Delete is hidden, not disabled, on an unsaved recipe.** `App.tsx`'s editor TopBar renders the Delete button only when `editor.storedId !== null`. A never-saved recipe has no server row to delete; a disabled-but-present button would imply otherwise. Condition is exactly `editor.storedId !== null` (strict `!==`, `null` is the only absent value).
10. **Success routing is explicit per family.** Profile form: on a resolved delete the manager calls its existing `onDeleted(id)` **and** `setFormTarget(null)`, returning to that manager's list. Recipe editor: on a resolved delete `App.tsx` calls `editor.closeEditor()` then `setView('list')`, returning to the library — bypassing `goToLibrary()` so the dirty-check `window.confirm` cannot ask the user to save a recipe that was just deleted.
11. **Failure retains state.** On a rejected delete the dialog closes, the form/editor stays open with the user's edits intact, and the error message renders in the form/editor. No navigation occurs. `ConfirmDialog` itself never swallows or renders the error; it only reports the user's choice.
12. **`TopBar.tsx` is NOT modified.** Delete uses the existing `children` (actions) slot. A dedicated named `delete` slot was considered and rejected: `TopBar` is a layout primitive with no per-action semantics, a `delete` slot would be the only action-specific prop on it, and `children` already renders an ordered flex row — ordering Delete first is a matter of JSX order at the four call sites. This keeps `TopBar` on the Untouched list for the first time since P3 modified it. Recorded as deviation register entry 3.
13. **`BatchList.tsx` is NOT modified.** BUG-007 names Batches among the lists to convert, but `BatchList` already renders a full-width `<ul className="divide-y">` of rows, not tiles — it was the only list already in the target shape. Retrofitting it onto `ListRow` would be churn with no user-visible change, and it has no edit-mode/delete flow for BUG-006 to touch. It inherits BUG-007's width fix through `PAGE_CONTAINER_CLASS` alone. Recorded as deviation register entry 4.
14. **Every datum visible on today's cards must remain visible on the new row.** Binding per-family field lists are given in §2.4. A field may be repositioned within the row; it may not be dropped. This is enforced by AC-24 through AC-27.
15. **Scope guardrail uses a SHA-256 content manifest, not `git diff --name-only`.** This repo has a single pre-M1 commit (`7d88e64`) and the entire M1–M5.5 body of work is uncommitted, so a diff against any base commit returns essentially the whole tree and proves nothing about this phase. The same reasoning established the manifest approach at M5.5_P1 (AC-33), P2 and P3 (AC-34). See AC-40.

## 2. Component Contracts

### 2.1 Pure-value contract — `PAGE_CONTAINER_CLASS`

```
export const PAGE_CONTAINER_CLASS: string
```

- Exact value: `'w-full px-4 sm:px-6 lg:px-8 py-6'`.
- Single frozen value. No variant prop, no second exported class, no conditional/computed width (Ambiguity 1).
- Consumed by `PageContainer` only. All existing `<PageContainer>` call sites compile and behave unchanged.

### 2.2 Pure-value contracts — `ListRow.tsx` classes

```
export const LIST_CONTAINER_CLASS: string
export const LIST_ROW_CLASS: string
```

- `LIST_CONTAINER_CLASS` — the `<ul>`/wrapper class for a list of rows. Binding requirements: full-width (`w-full`), a single outer border and rounding, `overflow-hidden`, and `divide-y divide-slate-800` so rows are separated by hairlines rather than gaps. It must **not** contain `grid`, `grid-cols-*`, `gap-*`, `max-w-*`, or `mx-auto`.
- `LIST_ROW_CLASS` — the row root class. Binding requirements: `w-full`, horizontal flex with the content group first and the `trailing` group last (`justify-between` or equivalent), dense vertical padding (`py-3`, strictly less than the current cards' `p-4`), a hover affordance, `cursor-pointer`, and `text-left`. It must **not** contain `rounded-*`, `shadow-*`, `border` (the divider comes from the container), `max-w-*`, or `mx-auto`.
- Both are frozen single values, same discipline as `PAGE_CONTAINER_CLASS`.

### 2.3 Component contract — `ListRow`

```
export interface ListRowProps {
  /** Stable test hook, e.g. `equipment-row-<id>`. Rendered as data-testid on the root. */
  testId: string;
  /** Accessible label for the row's open action, e.g. `Open "All-Grain 20L System"`. */
  label: string;
  /** Primary line — the entity name. */
  primary: ReactNode;
  /** Secondary dense metadata line. May be omitted. */
  meta?: ReactNode;
  /** Right-aligned nested controls. Each MUST stopPropagation in its own handler. */
  trailing?: ReactNode;
  /** Fired on click, Enter, or Space on the row root. */
  onOpen: () => void;
}
export function ListRow(props: ListRowProps): JSX.Element
```

Binding behaviour:

- Root element is `<div role="button" tabIndex={0} data-testid={testId} aria-label={label} className={LIST_ROW_CLASS}>` — a `<div>`, never a `<button>` (Ambiguity 2).
- `onClick` on the root calls `onOpen()` unconditionally. Nested controls prevent this by stopping propagation themselves; `ListRow` does **not** inspect `event.target` in `onClick`.
- `onKeyDown` calls `onOpen()` **iff** `event.target === event.currentTarget` **and** (`event.key === 'Enter'` **or** `event.key === ' '`). For `' '` it calls `event.preventDefault()` first. Every other key is a no-op.
- **Degenerate inputs:** `meta` omitted/`undefined` → no meta element rendered at all (no empty `<div>`, no placeholder text). `trailing` omitted/`undefined` → no trailing container rendered. Neither omission changes the row's height class or `onOpen` behaviour.
- `ListRow` is pure presentation: no internal state, no data fetching, no `window.*` call.

### 2.5 Component contract — `ConfirmDialog`

```
export interface ConfirmDialogProps {
  open: boolean;
  title: string;
  message: string;
  /** Label of the destructive button. Defaults to 'Delete'. */
  confirmLabel?: string;
  /** True while the confirmed action is in flight. Disables both buttons. */
  busy?: boolean;
  onConfirm: () => void;
  onCancel: () => void;
}
export function ConfirmDialog(props: ConfirmDialogProps): JSX.Element | null
```

Binding behaviour:

- `open === false` → returns `null`. Nothing rendered, no overlay, no `data-testid` present in the DOM.
- `open === true` → renders a `fixed inset-0` overlay containing `role="dialog"` `aria-modal="true"` with `data-testid="confirm-dialog"`, the `title` as its heading, the `message`, a Cancel button (`data-testid="confirm-dialog-cancel"`) and a destructive confirm button (`data-testid="confirm-dialog-confirm"`) labelled `confirmLabel ?? 'Delete'`.
- `busy === true` → **both** buttons `disabled`. `onConfirm` and `onCancel` must not be reachable while busy.
- `ConfirmDialog` is stateless and side-effect free: it never calls an API, never navigates, never renders an error. It reports the user's choice and nothing else (Ambiguity 11).
- It does **not** call `window.confirm`. Zero `window.confirm` calls may remain in the four delete paths (AC-13).

### 2.6 Shared contract — `DeleteAction`

Declared once in each of the three form files (Ambiguity/§1.4 note):

```
interface DeleteAction {
  /** Invoked only after the user confirms. Owns the API call. */
  onConfirm: () => void | Promise<void>;
  /** Non-null disables Delete and is used as its title. Null = deletable. */
  blockedReason: string | null;
  /** True while the delete request is in flight. */
  busy: boolean;
  /** Last delete failure message, or null. */
  error: string | null;
}
```

Present on the `edit` arm only; the `create` arm must not accept it, and TypeScript must reject passing it in create mode.

### 2.7 Stateful integration contract — the three profile managers

Written for `EquipmentManager`; `MashProfileManager` and `FermentationProfileManager` are identical modulo entity name, API function, testid prefix (`mash-` / `fermentation-`) and the `activeRecipeProfileId` prop name.

1. **List mode.** The `profiles.map` body renders `<ListRow testId={\`equipment-row-${profile.id}\`} ... onOpen={() => setFormTarget({ mode: 'edit', profile })} />` inside a `LIST_CONTAINER_CLASS` wrapper. The two action buttons, the amber in-row note, and the per-row `deleteError` panel are removed from the list. The existing `data-testid={\`equipment-row-${profile.id}\`}` string is preserved exactly, now carried by `ListRow`'s root.
2. **`isActive` is retained** as `profile.id === activeRecipeEquipmentId` but is now computed for the *form target*, not per row: when entering edit mode the manager derives `blockedReason = formTarget.profile.id === activeRecipeEquipmentId ? 'In use by the recipe currently open in the editor' : null`.
3. **`handleDelete(profile)`** keeps its body verbatim except: the leading `if (!window.confirm(...)) return;` line is **deleted**, and inside the `try` block, after `onDeleted(profile.id)`, it calls `setFormTarget(null)`. `deletingId`, `setDeleteError`, the `ApiClientError` message fallback, and the `finally { setDeletingId(null) }` are unchanged. On the catch path `setFormTarget(null)` is **not** called (Ambiguity 11).
4. **Edit-mode render** passes `deleteAction={{ onConfirm: () => handleDelete(formTarget.profile), blockedReason, busy: deletingId === formTarget.profile.id, error: deleteError?.id === formTarget.profile.id ? deleteError.message : null }}`.
5. **`deleteError` no-match contract:** when `deleteError` is `null`, or its `id` does not match the open profile, `error` is `null` — never `''`, never a placeholder string. The form branches on `error !== null` and renders no panel otherwise.
6. **Create mode** passes no `deleteAction`. The form must render no Delete button and no dialog in create mode.
7. TopBar title/leading/New-Profile button, `loadError` panel, empty state, and `onBack` are unchanged.

### 2.8 Stateful integration contract — `RecipeLibrary`

1. Rows render via `ListRow` inside `LIST_CONTAINER_CLASS`, replacing `grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 gap-4` and the per-card `bg-slate-900 border ... rounded-xl p-4 shadow-lg` wrapper.
2. `onOpen={() => handleOpen(r.id)}` — `handleOpen`'s body (including its `ApiClientError` → `onOpenError` path) is unchanged.
3. `trailing` is the Duplicate button only, calling `(e) => { e.stopPropagation(); handleDuplicate(r.id); }`. `handleDuplicate`'s body is unchanged.

## 5. Deviation Register

Each entry needs explicit sign-off or overrule at the halt gate.

1. **`RecipeLibrary`'s Duplicate action is retained.** BUG-006 names only Edit and Delete; `duplicateRecipe` has no other entry point in the app, so removing it would delete a capability the bug never asked to remove. It survives as the row's sole `trailing` control, subject to the `stopPropagation` rule (Ambiguity 2/4). **Alternative if overruled:** remove Duplicate too, accept the capability loss, and drop AC-11/AC-18.
2. **`RecipeLibrary`'s inline rename (the `Pencil`) is removed and its `patchRecipeName` call site with it.** BUG-006 names "Edit (pencil)"; in this file the pencil is a rename, not an edit-mode entry. Removal is justified because the editor already owns an editable name input (AC-19), but this is a real interaction the user loses from the list view. **Alternative if overruled:** keep rename as a second `trailing` control alongside Duplicate.
3. **`TopBar.tsx` is not modified — Delete uses the existing `children` slot.** A named `delete` slot was considered and rejected (Ambiguity 12). This puts `TopBar` back on the Untouched list after P3 modified it. **Alternative if overruled:** add an optional `destructive?: ReactNode` slot rendered before `children`.
4. **`BatchList.tsx` is not modified**, despite BUG-007 naming Batches. It is already a full-width divided list and has no edit/delete flow; it gets the width fix through `PAGE_CONTAINER_CLASS` alone (Ambiguity 13). **Alternative if overruled:** retrofit `BatchList` onto `ListRow` (adds 2 files to §1.2 and requires `BatchList.test.tsx` locator updates).
5. **One shared row component across all four entity families, not four similar ones.** `ListRow` is deliberately generic (`primary`/`meta`/`trailing`/`onOpen`) so the combined BUG-006+BUG-007 interaction pattern exists in exactly one place and cannot drift — the same "make the inconsistent case unrepresentable" reasoning P3 used for `PAGE_CONTAINER_CLASS`. Cost: the four families' rows can no longer diverge without touching a shared primitive. **Alternative if overruled:** four per-family row components, accepting four copies of the click/keyboard/stopPropagation logic.
6. **This phase supersedes M5.5_P3's `PAGE_CONTAINER_CLASS` decision, explicitly.** P3's deviation 2 froze `max-w-7xl` as a single value with no variant. BUG-007 revises that value. The *freeze* is retained (still one constant, still no variant); only the *value* changes, to `'w-full px-4 sm:px-6 lg:px-8 py-6'`. Flagged so the critic reads P3's constant as superseded rather than violated (Ambiguity 1). **Alternative if overruled:** keep `max-w-7xl` and close BUG-007 on the list-shape half only.
7. **`window.confirm` → `ConfirmDialog` for the four delete flows only.** `App.tsx`'s unsaved-changes `window.confirm` stays as-is, leaving the app with two confirmation mechanisms (Ambiguity 8). **Alternative if overruled:** convert the dirty-navigation confirm too — but that reopens M5.5_P2 deviation 1's deliberately deferred unsaved-changes-guard question and should get its own phase.
8. **The recipe Delete lands in `App.tsx`, not in a form component.** Recipes have no `RecipeForm`; their edit mode *is* the editor route, which `App.tsx` owns. This makes `App.tsx` the one place where the delete state (`recipeDeleteOpen`/`Busy`/`Error`) lives beside route state rather than in a manager. **Alternative if overruled:** extract a `RecipeEditorTopBar` component first — larger diff, no user-visible difference.
9. **`handleRecipeDeleted` is retained in `App.tsx` despite losing its only caller.** Deleting it would be a plausible tidy-up that the manifest sweep would flag; §2.9.6 forbids it without an amendment. **Alternative if overruled:** remove it and note the removal in §1.4.
