# FEATURE SPECIFICATION: M5.5_P5 — Batch Detail opens directly in edit mode

## Phase Summary

This phase closes **BUG-011**. Opening a batch currently lands on a read-only `<dl>` summary; reaching the editable form requires a second click on an "Edit Batch" button in `TopBar`. Every other editable surface in the app — the Recipe Editor and the three profile forms (`EquipmentForm`, `MashProfileForm`, `FermentationProfileForm`) — is "always editable, no separate view mode". `BatchDetail` is the last holdout.

The mechanical core is small and was already proven out under the lightweight-task exception (rule 7) and then **fully reverted**: initialize the form data when the batch loads instead of on a button click, and drop the view-mode gate. The reason that attempt was reverted is not that the mechanism was wrong — it is that **50 of `BatchDetail.test.tsx`'s 56 tests are structurally coupled to the old default**, and that two genuine design questions (what Save/Cancel mean once there is no view mode; whether the Edit Batch button survives at all) were being answered implicitly by a diff rather than deliberately by a spec. Both are answered as binding Resolved Ambiguities below.

The single largest source of that 50-test breakage is not the button. It is that **`'Batch Details'` — the `<h3>` heading of the read-only `<dl>` block — is the `await waitFor(...)` load anchor in roughly 40 tests.** Removing the read-only block removes that string from the DOM, so every one of those tests times out at its first `await`, regardless of what it goes on to assert. The rewrite is therefore overwhelmingly a **mechanical anchor substitution**, not 50 tests' worth of new logic. §3.7 categorizes every block precisely.

This phase is presentation/state-mechanics only. `updateBatch`'s call shape, the PUT payload, the four separated error states, the `useMemo` figure-resolution branch point, the stepper, the measurement inputs, `MeasuredComparison`, `CarbonationPanel`, `ReadingLog`, `FermentationChart`, `BatchNoteLog` and `BatchStepper` are all behaviorally unchanged.

### Key Behaviors

1. **A loaded batch renders its editable form immediately.** No click, no intermediate state. The form is what `BatchDetail`'s loaded state *is*.
2. **View mode is deleted, not merely bypassed.** The read-only `<dl>` block, its `Batch Details` heading, the `editMode` state, `handleEdit`, `displayData` and the `editButton` JSX are removed from the source file. Nothing in the page can reach a read-only rendering of the batch's measurements.
3. **Save stays in the form.** A successful `updateBatch` repopulates `formData` from the server response and leaves the user on the same editable form — the Recipe Editor / profile-form pattern.
4. **Cancel becomes an explicit discard-my-edits control, renamed accordingly.** It reverts `formData` to the last-loaded/last-saved server state and stays in the form. It never navigates and never calls the API.
5. **The `TopBar` action slot keeps only the status badge.** The Back control (`leading`) and the status badge (`children`) are unchanged; the Edit Batch button is gone from the slot and from the file.
6. **No datum visible today is lost.** Every field in the removed `<dl>` already exists as a form control except `bottlingDate`, which is read-only server state with no input. It is preserved as a read-only line inside the form (§2.4), keeping its `data-testid="display-bottling-date"`.

### Resolved Ambiguities (Binding)

1. **View mode is REMOVED from the page entirely. Save does not exit to it; there is nothing to exit to.**
   `handleSave`, on a resolved `updateBatch`, sets `batch` to the server response, sets `formData` from that same response, and clears `saveError`. It does **not** set any mode flag, because no mode flag exists after this phase. Reasoning: with entry defaulting to edit, a view mode reachable only via Save-success or Cancel is a state the user can enter but has no deliberate way to re-enter *or* recognize — and with the Edit Batch button removed (Ambiguity 2) it would be a state with no exit at all except a full page reload. Retaining it would also mean this page keeps a second, divergent rendering of the same nine measurements that no other editable surface in the app has. Recorded as deviation register entry 1.
2. **The "Edit Batch" button is DELETED OUTRIGHT — the element, its `editButton = !editMode && (...)` binding, its `handleEdit` handler, and its position in the `TopBar` children slot.** It is not left conditionally-never-rendered and not left commented out. Reasoning: a control whose only purpose was to enter a state that no longer exists is dead code, and dead-but-present UI code is exactly what a later reader restores by accident. `TopBar`'s children slot then contains `{statusBadge}` alone. Recorded as deviation register entry 2.
3. **The read-only `<dl>` block is DELETED, along with its `Batch Details` heading, its wrapper card, and the `displayData` local.** With Ambiguities 1 and 2 resolved, it is unreachable. `displayData` (`currentData ?? batch`) has no other consumer in the file and is removed with it. `currentData` is **retained** — the `useMemo` still reads it for the live efficiency preview. Recorded as deviation register entry 3.
4. **The `Batch Details` string is NOT re-added anywhere as a heading over the form.** Re-adding it would silently preserve ~40 test anchors while masking the very removal this phase is auditing. The load anchor becomes `data-testid="batch-detail-form"` on the `<form>` root (§2.3). AC-9 asserts `Batch Details` appears nowhere in the rendered output or the source.
5. **The "Cancel" button is renamed to "Discard Changes"** and its behavior redefined as: `setFormData(<fields projected from the current `batch`>)`. No API call, no navigation, no mode change. Reasoning: with no view mode, "Cancel" has no destination and reads as "leave this page" (which is what the Back control does) rather than "throw away my unsaved edits", which is now its only meaning. Leaving the page is `TopBar`'s Back control and is untouched. Recorded as deviation register entry 4. **Alternative if overruled:** keep the literal label `Cancel` with identical behavior; only AC-13's name string changes.
6. **`formData` stays typed `BatchWriteInput | null`.** It is `null` only before the initial fetch resolves — the same window in which `batch` is also `null` and the component early-returns `Loading...`. It is **not** widened to a non-nullable type and **not** given a synthetic empty-batch default: a fabricated placeholder is exactly the kind of value that leaks into a PUT body. The form JSX is guarded `{formData && (<form …>)}`; `batch` and `formData` are set in the **same** `.then` callback so they can never be observed in disagreement.
7. **`formData` is populated from the loaded batch, not two-way-bound to it.** The projection is the exact same 14-field object literal `handleEdit` builds today (§2.2), moved to the load path and the save path. Field set, field order and null-handling are byte-identical to the current `handleEdit` body. No field is added or dropped from the PUT payload.
8. **Hooks order is unchanged and remains unconditional.** No hook is added, removed, or moved. `useState` count stays at 8, `useEffect` at 1, `useMemo` at 1 — with `editMode`'s `useState` removed and **no** replacement, the count drops to 7 `useState` calls. All remain above the `if (error) {` early return. The two existing source-sweep tests (`AC-39`, `AC-42`) that assert this must continue to pass **unmodified**, including their `source.indexOf('\n  if (error) {')` locator. This is the file's documented critic-caught regression (hooks-count mismatch between the loading render and the loaded render); it is a hard constraint on the diff, not a suggestion.
9. **`bottlingDate` is preserved as a read-only line inside the form.** It is the one datum in the removed `<dl>` with no corresponding input (it is server-assigned on the Conditioning transition). Dropping it would be a silent capability loss disguised as a layout change. Same "no datum visible today may be dropped" principle M5.5_P4 Ambiguity 14 established. Recorded as deviation register entry 5.
10. **Scope guardrail uses a SHA-256 content manifest, not `git diff --name-only`.** This repo has a single pre-M1 commit (`7d88e64`); the entire M1–M5.5 body of work is uncommitted, so a diff against any base commit returns essentially the whole tree and proves nothing about this phase. Established at M5.5_P1 (AC-33) and carried through P2/P3/P4. See AC-26.
11. **`apps/web/test/App.test.tsx` requires NO change.** Verified by search: no file other than `BatchDetail.tsx` and `BatchDetail.test.tsx` references `'Edit Batch'` or `'Batch Details'`. `App.test.tsx`'s batch-detail integration tests anchor on the `<h1>` accessible name and on `topbar-lead`/`page-container` testids — all unaffected — and its three source-text sweeps over `BatchDetail.tsx` assert only "no `<h1`" and "renders `PageContainer`", both still true. `App.test.tsx` is on the Untouched list (§1.3) and AC-26 enforces it.

## 2. Behavioral Contract — `BatchDetail`'s state machine

### 2.1 The state machine, post-change

`BatchDetail` has exactly **three** renderable states, down from four. There is no mode flag.

| State | Entered when | Renders |
|---|---|---|
| **Loading** | `error === null && batch === null` | `TopBar title="Batch"` + Back, `PageContainer` with `Loading...`. Unchanged from today. |
| **Error** | `error !== null` | `TopBar title="Batch"` + Back, `PageContainer` with `Error: {error}`. Unchanged from today. Takes precedence over Loading (it is the first early return). |
| **Loaded (editable)** | `error === null && batch !== null` | `TopBar title={batch.name}` + Back + status badge; the editable form; the comparison/carbonation grid; the fermentation panel; reading log; note log. |

The previously-existing fourth state — *Loaded (read-only)* — is removed. There is no input, transition or failure path that reaches a read-only rendering of the batch's measurements.

Invariant, binding: **`formData !== null` ⟺ `batch !== null`.** Both are set in the same `.then` callback and neither is ever set back to `null`. The form JSX guard `{formData && …}` therefore never renders `false` in a state a user can observe; it exists solely to narrow the type for TypeScript (Ambiguity 6).

### 2.2 The `formData` projection — binding

Exactly these 14 fields, in this order, sourced from a `BatchWithReadings`:

`name`, `status`, `measuredPreBoilGravity`, `measuredMashPh`, `measuredBoilSizeL`, `measuredBoilTimeMin`, `measuredOg`, `measuredFg`, `measuredBottlingSizeL`, `carbonationType`, `carbonationVolumesTarget`, `carbonationTempC`, `tasteNotes`, `tasteRating`.

Byte-identical to the current `handleEdit` body. No field added, dropped, defaulted or coerced. `null` fields project as `null`, never as `''` or `0`. This projection is used at exactly **three** call sites: the load `.then`, `handleSave`'s success path, and `handleCancel`. The executor may factor it into one local helper or inline it three times — either satisfies this spec; what may not vary is the field set.

### 2.3 Load path

1. `getBatch(batchId)` resolves with `b` → `setBatch(b)` **and** `setFormData(<projection of b>)`, in the same callback.
2. `getBatch` rejects → `setError(...)` exactly as today. `formData` is never populated; the Error state early-returns before the form.
3. `batchId` changing re-runs the effect (dependency array unchanged: `[batchId]`), re-populating both — a batch switch therefore discards unsaved edits to the previous batch. This is the pre-existing behavior of the `[batchId]` effect and is not extended.
4. The `<form>` root carries `data-testid="batch-detail-form"`. This is the canonical load anchor for tests.

### 2.4 The Bottling Date line (Ambiguity 9)

Rendered inside the form, in the "Conditioning & Carbonation" section, alongside the four existing controls there. It is a labelled read-only value, **not** an `<input>` and **not** a disabled input (a disabled input implies a field that could become editable). Content is byte-identical to today's `<dd>`:

`batch.bottlingDate !== null ? new Date(batch.bottlingDate).toLocaleString() : '-'`

sourced from `batch` (not `formData` — it is not a form field), carrying `data-testid="display-bottling-date"`, with a visible label reading `Bottling Date`.

### 2.5 Save / Discard contract

**`handleSave(e)`** — form `onSubmit`:

| Step | Behavior |
|---|---|
| Guard | `e.preventDefault()`; `if (!formData) return;` — unchanged. |
| Busy | `setIsSaving(true)` … `finally { setIsSaving(false) }` — unchanged. |
| Call | `await updateBatch(batchId, formData)` — argument shape unchanged, payload unchanged. |
| Success | `setBatch(updated)`; `setFormData(<projection of updated>)`; `setSaveError(null)`. The user remains on the same form, now showing the server's canonical values (so a server-side coercion or a status transition is visibly reflected in the inputs). |
| Failure | `setSaveError(message)` **only**. `error` is not touched (the page must not blank — the file's documented F-2 finding). `formData` is left exactly as the user typed it; no revert on failure. |

**`handleCancel()`** — the `Discard Changes` button, `type="button"`:

| Step | Behavior |
|---|---|
| Action | `setFormData(<projection of the current `batch`>)`. |
| Not done | No API call. No navigation. No `setBatch`. No mode change (none exists). `saveError` is **not** cleared — a discard is not a retry, and silently clearing the last failure message would hide why the user is discarding. |
| Result | The form re-renders showing the last server-known values; unsaved edits are gone; the user is still on the editable form. |

**`handleEdit`** — does not exist after this phase.

### 2.6 Everything downstream of the form is unchanged

The `useMemo` figure-resolution block, its dependency array `[batch, currentData]`, its `closingSnapshot` branch and its AC-38 formula-immunity property are **not** modified. Note the one behavioral consequence the executor must understand and must not "fix": `currentData` (`formData ?? batch`) now resolves to `formData` from the first loaded render onward rather than only while editing. Because the projection copies `batch`'s values verbatim, the memo's inputs on the first loaded render are value-identical to today's; the live-efficiency preview and the frozen-figure branch behave exactly as before. No dependency array, no branch condition, and no call-count property changes.

`MeasuredComparison`, `CarbonationPanel`, `FermentationChart`, `ReadingLog`, `BatchNoteLog` and `BatchStepper` receive the same props from the same sources. The four separated error states keep their separation.

## 5. Deviation Register

Each entry needs explicit sign-off or overrule at the halt gate.

1. **View mode is removed from the page entirely; Save no longer exits to a read-only summary.** BUG-011 left this open. Chosen because a mode reachable only by Save-success or Cancel, with no button left to re-enter it, is a state the user cannot navigate deliberately — and once the Edit Batch button is deleted (entry 2) it would have no exit short of a reload. It also aligns `BatchDetail` with the Recipe Editor and the three profile forms, which is the stated motivation of the bug. **Cost:** there is no longer any compact, non-editable overview of a finished batch's measurements; a completed batch is presented as an editable form. **Alternative if overruled:** keep `editMode`, default it to `true`, and keep Save/Cancel dropping to the read-only `<dl>` — which retains AC-25's count roughly as-is but leaves the page with a state whose only entrances are Save and Cancel and whose only exit is a reintroduced Edit Batch button.
2. **The "Edit Batch" button, `handleEdit`, and the `editButton` binding are deleted outright**, not left conditionally-never-rendered. **Cost:** `M5.5_P3 AC-19` — a criterion a prior phase in this same milestone deliberately specified and verified — is retired one phase later. That is flagged here explicitly so the critic reads it as superseded by this spec rather than violated: P3 moved the button into `topbar-actions`; P5 removes the button. `TopBar.tsx` itself is untouched and its actions slot still works — `BatchDetail` now passes it only the status badge. **Alternative if overruled:** retain the button as a no-op-free "Reload from server" control (a different feature, needing its own AC).
3. **The read-only `<dl>` block and the `displayData` local are deleted.** Unreachable after entries 1 and 2; leaving unreachable UI in place is how it gets restored by accident later. **Cost:** three `data-testid`s (`display-measured-fg`, `display-taste-notes`, `display-taste-rating`) disappear, and four existing assertions retarget to the corresponding form controls (§3.7 category B). **Alternative if overruled:** keep the block rendered *below* the form as a permanent summary — which reintroduces two renderings of the same nine values that must be kept in agreement, the exact duplication this phase removes.
4. **The Cancel button is renamed to "Discard Changes".** With no view mode, "Cancel" has no destination and collides in meaning with the TopBar Back control. **Cost:** a visible label change the bug did not ask for, and one new button-name locator in the tests. **Alternative if overruled:** keep the literal label `Cancel`, identical behavior; only AC-13's name string changes.
5. **`bottlingDate` is preserved as a read-only line inside the form.** It is the only datum in the removed `<dl>` with no corresponding input. **Cost:** the form now contains one non-input, read-only row, which is a small inconsistency inside an otherwise all-editable surface. **Alternative if overruled:** drop it, accept that `batch.bottlingDate` becomes invisible in the UI, and remove AC-11.
6. **`saveError` is deliberately NOT cleared by Discard Changes.** A discard is not a retry; clearing the banner would remove the explanation of *why* the user is discarding, and the next successful save clears it anyway. **Alternative if overruled:** have `handleCancel` also call `setSaveError(null)` and invert AC-16.
7. **Six new tests are added rather than folding the new coverage into rewritten blocks.** Keeping the new default-entry, Save and Discard properties in their own named blocks means the critic can see at a glance which coverage is new and which is a retargeted old assertion, and makes the 61 count auditable against §3.7's arithmetic. **Alternative if overruled:** fold them into existing blocks and restate AC-25's expected count.
