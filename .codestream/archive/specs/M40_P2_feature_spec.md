# FEATURE SPECIFICATION: M40_P2 — The fragile pair survives a 375px thumb

## Phase Summary

Milestone 40 Phase 1 raised `CONTROL_HEIGHT_CLASS` to `h-11` (44px) and fixed six named layout sites. That change reaches every control that is *built from a `ui/` primitive*. Phase 2 addresses the two files the roadmap deliberately isolated — `apps/web/src/App.tsx` (1,016 lines) and `apps/web/src/pages/BatchDetail.tsx` (1,569 lines), the two highest-regression-risk surfaces in the app — where a measurable number of controls **bypass the primitives entirely** and therefore did not move when the token moved.

Source-verified inventory (this session, against the current working tree):

- **`App.tsx` carries five raw `<button>` elements** with hand-rolled Tailwind: the recipe-editor back arrow (`p-2`, line 650), Delete (`px-3 py-2`, line 662), Scale Batch (`px-3 py-2`, line 675), Brew This (`px-3 py-2`, line 681), and the "no equipment profiles" call-to-action (`px-3 py-1.5`, line 467). Four of the five sit in the recipe editor's `TopBar` — the most-tapped strip in the designer. These are a **known, documented, never-closed exemption**: `uiPrimitives.test.tsx:907` asserts "AC-16: App.tsx scale modal renders through Button/NumberInput (**raw buttons outside the modal remain, per RA-5**)". Phase 2 closes that exemption.
- **`App.tsx` carries one raw `<select>`** (line 854, the Equipment Profile picker, `px-2.5 py-1 text-xs` — roughly a 26px tap target) and **three raw underline `<input>`s** (recipe name line 739, style line 757, brewer line 769), the latter carrying an in-file comment that names them as deliberately-untouched leftovers while the adjacent folder/tag controls were migrated onto the `Input` primitive in M38_P3.
- **`BatchDetail.tsx` carries exactly one raw `<button>`** (line 1065, the identity-edit trigger). It is a full-width card-sized hit area already marked `data-ignore-raw-button`, i.e. an existing, honoured sweep exemption. It is **not** changed by this phase.
- **Breakpoint counts, re-verified:** `App.tsx` now has **one** breakpoint (`sm:min-w-[280px]` at line 738, added by P1); `BatchDetail.tsx` has **six**, and every one of its six grids already declares a mobile base (`grid-cols-1` ×4, `grid-cols-2` ×1, `flex-col sm:flex-row` ×1). **Neither file needs new breakpoints added.** The roadmap's premise that these files need responsive breakpoints retrofitted is **false as of today's tree** — what they actually need is (a) their bespoke controls routed through the design system, and (b) minimum-width intrinsic-sizing guards so long unbreakable strings cannot force a horizontally-scrolling page.

The user-visible outcome: on a 375px phone, the recipe editor's header actions and equipment picker, and the batch workbench's identity block and metric tiles, are consistent, thumb-sized design-system controls that do not push the page sideways — instead of one-off markup the 44px token never reached.

### Key Behaviors

1. Every interactive control in `App.tsx` is rendered by a `ui/` primitive (`Button`, `Select`, `Input`), not by hand-written Tailwind — so it inherits whatever the control-height token is now and whatever it becomes later, with no per-site edit.
2. The Equipment Profile picker in the recipe editor becomes a real 44px `Select`.
3. Long, unbreakable recipe/batch names and metric values can no longer widen a flex or grid track past its share of a 375px viewport.
4. A static sweep proves the raw-control exemption for `App.tsx` is gone and cannot silently return.
5. Nothing else in the app changes. No new breakpoints, no structural re-sectioning, no `SectionCard` introduction (see RA-3).

### Resolved Ambiguities (Binding)

- **RA-1 — `SectionCard` progressive disclosure is DECLINED for both files, with reasons.** The roadmap flags `SectionCard`'s `collapsible`/`defaultOpen` (M39_P1) as "an option to weigh at `/plan`, not a mandate". Weighed against the actual source, and declined for both:
  - **`BatchDetail.tsx` already has progressive disclosure** — `BatchStageTabs` renders exactly one of five stage panels at a time (`batch-tab-panel-planning|brewing|fermentation|packaging|completed`), and no panel holds more than five cards. Adding a second collapse layer inside a tab that already shows ≤5 cards adds taps without removing scroll.
  - **`App.tsx` does not own any section cards.** Its editor route composes `FermentableSection`, `HopSection`, `YeastSection`, `MiscSection`, `MashSection`, `WaterSection`, `StatsHeader` and `StyleTargetPanel`. Four of those already render `SectionCard` **inside their own files**. Making them collapsible therefore means editing *those* files, not `App.tsx` — which is outside this phase's isolation rationale entirely.
  - Consequence: `SectionCard.tsx` and every current `SectionCard` consumer are untouched by this phase (AC-14).
- **RA-2 — No new breakpoints are added to either file, and this is a deliberate finding, not an omission.** The roadmap's hardening scope was written when both files were believed to carry zero breakpoints. `App.tsx` has one (P1's) and needs no more: its route wrappers are `flex-1 flex flex-col h-full overflow-hidden min-w-0` single columns, its two multi-item rows (`flex flex-wrap` at lines 737 and 754) already wrap, and it declares **zero** `grid-cols-*` anywhere. `BatchDetail.tsx` has six, all already mobile-first. Adding speculative breakpoints to a 1,569-line file to satisfy a stale line in the roadmap would be pure regression risk with no user-visible outcome. The roadmap's Milestone 40 section is corrected in the same sitting as this spec.
- **RA-3 — The real 375px failure mode in these two files is intrinsic minimum sizing, not missing breakpoints.** Flex and grid children default to `min-width: auto`, so a child's longest unbreakable content sets a floor its track cannot go below; the excess escapes as *page* horizontal scroll, which is exactly what Milestone 40's verification threshold forbids. Three sites qualify and are the only layout edits in this phase:
  1. `BatchDetail.tsx:1074` — the batch name at `text-2xl font-bold` inside a `flex flex-wrap items-center gap-3` row, with no `min-w-0` and no wrapping rule.
  2. `BatchDetail.tsx:1345` — the four live-fermentation metric tiles at `grid-cols-2` (≈141px of content per cell at 375px), whose children carry no `min-w-0`.
  3. `App.tsx:850` — the Equipment Profile block, `flex items-center gap-3` with no `min-w-0` on its text column, sitting as a wrap sibling of the 280px recipe-name column.
  The binding fix is `min-w-0` on the shrinkable child plus `break-words` on the two free-text name renders. It is **not** `overflow-x-auto` — clipping the page is not the same as fitting it, and `PageContainer` remains the sole scroll owner (M28).
- **RA-4 — Migrating `App.tsx`'s raw buttons onto `Button` does NOT by itself make them 44px, and this spec does not claim it does.** The `Button` primitive sizes by padding only (`BUTTON_PRIMARY_CLASS` = `px-4 py-2`; `size="sm"` = `text-xs px-3 py-1.5`), references `CONTROL_HEIGHT_CLASS` nowhere, and therefore computes to roughly 40px (`md`) and 28px (`sm`) — **below 44px, app-wide, today.** P1's `controlTargetSize.test.ts` sweep cannot see this: it only flags explicit sub-44px *height classes* (`h-10`/`h-9`/`h-8`/`min-h-10`), and a padding-sized button declares none. This is a genuine, currently-open gap against Milestone 40's "zero interactive controls compute below 44px" threshold. **It is deliberately NOT in this phase** — see RA-5. What this phase delivers is the prerequisite: once `App.tsx`'s five bespoke buttons route through the primitive, a single later token change reaches them. Accordingly, **no acceptance criterion in this matrix asserts a 44px height for any `<button>`.**
- **RA-5 — Milestone 40 needs a third phase, and this is flagged for the user rather than force-fitted here.** Raising the `BUTTON_*_CLASS` tokens to ≥44px is a `designSystem.ts` + `Button.tsx` change with app-wide blast radius and a test-reconciliation surface at least as large as P1's five files — that is P1-shaped work (one token file, global propagation), and folding it into the phase that exists specifically to isolate the two fragile files would re-create exactly the confounding the split was designed to prevent. It also has a real ordering dependency on this phase: a token raise cannot reach five buttons that bypass the token. **Recommendation: M40 becomes 3 phases** — P3 raises the button/icon-button control-height tokens app-wide, extends `controlTargetSize.test.ts` to resolve padding-derived heights (not just `h-N` classes), and reconciles the affected tests. `ROADMAP.md`'s "Estimated phases" line for Milestone 40 is updated to 3 in the same sitting as this spec. If the user prefers to close M40 at two phases, P3's content should be logged to `FEATURES.md` rather than dropped.
- **RA-6 — The `underline` `Input` variant is an explicit, enumerated height exemption, not a silent one.** `INPUT_UNDERLINE_CLASS` deliberately omits `CONTROL_HEIGHT_CLASS` (see `ui/Input.tsx`) because it renders borderless inline metadata, not a boxed field — the same knowing WCAG 2.5.5 deviation already carried for `INPUT_COMPACT_CLASS` and `FORM_SELECT_COMPACT_CLASS` under P1's RA-9. Migrating `App.tsx`'s three raw metadata inputs onto `Input variant="underline"` therefore does not raise them to 44px. The binding requirement is that the exemption become **enumerated and asserted** (AC-11) rather than implicit, so the next reader finds a documented list rather than a gap.
- **RA-7 — The recipe-name input keeps its visual weight through `className`, not through staying raw.** `Input variant="underline"` composes `w-full` plus `INPUT_UNDERLINE_CLASS`. The name field's `text-2xl font-bold text-white py-0.5` is passed through `className` (which `Input` appends last, so it wins). Visual output must be unchanged; this is a markup-provenance change, not a restyle.
- **RA-8 — jsdom performs no layout, so no AC in this matrix asserts a measured pixel width or a scroll offset.** `getBoundingClientRect()` returns zeros under the suite. Every layout AC here is a **static source/class assertion**; real 375px confirmation is the manual on-device evidence in AC-15/AC-16, exactly as P1's RA-8 established. An AC that claimed a rendered width would be unfalsifiable and is therefore not written.
- **RA-9 — `BatchDetail.tsx`'s one raw `<button>` (line 1065) stays raw.** It is the identity-edit trigger: a `w-full text-left` region wrapping the batch name, status badge and metadata line — a card-sized hit area, not a control, and already marked `data-ignore-raw-button`, an exemption the existing sweep at `uiPrimitives.test.tsx:1107` honours by design. Converting it to `Button` would wrap block content in an `inline-flex items-center justify-center` container and visibly break the card. Untouched.
- **RA-10 — The scope guardrail uses a SHA-256 content manifest, NOT `git diff` against a base commit — checked, not assumed.** `git log` shows `a9091a1` ("Milestone 39 completed") as HEAD, but **M40_P1's 18 files are still uncommitted in the working tree** (`git status --porcelain -- apps packages` returns all 18). A `git diff --name-only a9091a1` would therefore report P1's files alongside P2's and could not isolate this phase's scope — the method P1 legitimately used is *not* viable for P2. Binding method: the executor takes a manifest with `git ls-files -co --exclude-standard -z | xargs -0 sha256sum > /tmp/m40p2_pre.sha256` **before its first edit**, repeats it to `/tmp/m40p2_post.sha256` at the end, and diffs the two. AC-17 is satisfied only by that pre/post manifest diff.
- **RA-11 — AC-15 (LAN reachability) and AC-18 (P1's six named-surface screenshots) from M40_P1 are explicitly NOT in this matrix.** They remain M40_P1's own outstanding items, pending the user's real-hardware confirmation, tracked independently of this phase. This phase carries its own, separate screenshot requirements (AC-15/AC-16 below) covering only the surfaces it touches. Nothing here blocks on, or discharges, P1's pair.
- **RA-12 — `BUGS.md` / `FEATURES.md` reviewed; nothing pulled in.** `FEAT-026 §1` (Recipe Designer TopBar action hierarchy — overflow menu for Delete/Scale at tablet widths) and `BUG-040 §2` (TopBar responsive shell with secondary-action overflow) both name `App.tsx`'s header, but both require restructuring `TopBar.tsx` (out of scope) and introduce a new overflow-menu affordance — new behaviour, not hardening. `FEAT-036`/`FEAT-041` name `BatchDetail.tsx` but are already-delivered items. None is moved to `IN_PLANNING` by this phase. This phase's `App.tsx` header work is provenance-only (raw → primitive) and deliberately does not change the action set, its order, or its wrap behaviour.

## 5. Phase-count implication (for the user, at the halt gate)

Per RA-4/RA-5: the `Button` primitive computes to ~40px (`md`) and ~28px (`sm`) and is **below Milestone 40's 44px threshold app-wide** — a real gap P1's sweep structurally cannot detect, because it only flags explicit `h-N` classes and `Button` sizes by padding. Closing it is a single-token-file change with global blast radius, which is P1-shaped work and would confound the fragile-pair isolation this phase exists to preserve; it also depends on this phase, since a token cannot reach five buttons that bypass it. **Milestone 40 is therefore recommended as 3 phases, not 2**, with `ROADMAP.md` updated accordingly. If the user prefers to close M40 at two phases, P3's content should be logged to `FEATURES.md` rather than dropped, and Milestone 40's verification threshold amended to say so.
