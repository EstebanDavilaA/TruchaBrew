# FEATURE SPECIFICATION: M5.5_P3 — One shell, one container, one place for every page control

- **Milestone:** M5.5 (Post-MVP Navigation & UI System Harmonization)
- **Phase:** P3 (closes `BUG-005`)
- **Depends on:** M5.5_P1 (`Sidebar.tsx` + `TopBar.tsx` shell, built, gates green, not yet `/verify`-ed) and M5.5_P2 (three profile forms converted modal → full page, each manager/form rendering its own `TopBar`, built, gates green, not yet `/verify`-ed). This spec composes with the code as it actually exists on disk today, which was read in full before drafting.
- **Layer:** presentation only. `apps/api/`, `packages/calculations/`, `packages/shared-types/` and every `drizzle/` directory are read-only in this phase.

## Phase Summary

`TopBar` exists but is used inconsistently. Today, by direct inspection:

- `App.tsx` renders `<TopBar title="Recipe Library" />` for the `list` route, while `RecipeLibrary.tsx` renders its own search input and `+ New Recipe` button inside a floating `bg-slate-900 … rounded-xl` card in the page body (`RecipeLibrary.tsx:98-117`).
- `App.tsx` renders a title-less `<TopBar />` for `batches` and `batchDetail`, while `BatchList.tsx:34-41` renders a body `← Back` button plus its own `<h1>Brewing Batches</h1>`, and `BatchDetail.tsx:362-387` renders a body `← Back` button, its own `<h1>`, a status badge and the `Edit Batch` action.
- The three managers (M5.5_P2) do put title / back / `New …` in `TopBar` — the pattern this phase generalises — but wrap their body in `max-w-4xl`.
- Container widths across the seven routes are `max-w-7xl` (list, editor), `max-w-4xl` (three managers, three forms), `max-w-5xl` (batchDetail) and `max-w-7xl` with `py-8` instead of `pt-6` (batches). Vertical padding varies (`pt-6` vs `py-8`).

This phase makes one rule true everywhere:

1. **Every route's chrome lives in `TopBar`** — title, the back/cancel control (sub-views only), search/filters, and the primary action. Nothing of that kind renders in a page body.
2. **Every route's content lives in exactly one `PageContainer`** — a new shared layout primitive with a single width and a single padding scale, so all seven routes align identically on a wide monitor.

`TopBar` gains exactly one new optional prop (`search`) and three `data-testid` hooks; nothing else about its contract changes. No new colour, no new dependency, no route-state change, no data-flow change.

### Key Behaviors

- The search input that filters the recipe library sits in `TopBar`'s search slot; typing in it filters exactly as it does today (same 200 ms debounce, same `listRecipes(q)` call).
- `+ New Recipe` sits in `TopBar`'s action slot and keeps its `canCreate` disabled semantics (M3_P1's AC-46 guarantee) verbatim.
- No page body anywhere in the app renders a back control; the only back/cancel affordance is `TopBar`'s `leading` slot.
- On a 1600 px-wide window, the content column of Recipes, Batches, a batch's detail, Equipment Profiles, Mash Schedules, Fermentation Schedules, the recipe editor and all three profile forms starts and ends at the same x-coordinates.

### Resolved Ambiguities (Binding)

1. **Scope is all seven routes, not a subset.** BUG-005's headline claim ("every page") is broad, and this spec deliberately accepts the full breadth rather than narrowing it, because the phase's central acceptance criterion — *every* route uses the same container — is not partially satisfiable. A half-pass would leave the bug open and produce an AC matrix whose most important entries are untestable. The cost is bounded and honest: **2 new files and 16 modified files**, all under `apps/web`, all presentation-layer, no schema/API/calculation surface. The scope is nonetheless narrowed in three specific, named ways, each in the deviation register: the batch-edit form's own `Cancel` / `Save Measurements` footer stays where it is (deviation 4); the three managers keep their `leading` back control despite being top-level nav destinations (deviation 5); and no empty/error-state visual redesign is attempted beyond re-homing existing markup (deviation 6).
2. **One container width for all seven routes, no size variants.** `PAGE_CONTAINER_CLASS` is a single frozen string. `PageContainer` takes **no** width prop, **no** `className` passthrough and **no** variant — a second width is exactly the mechanism that produced BUG-005, so the primitive must make the inconsistent case unrepresentable. Consequence, accepted: the three profile forms and the batch detail widen from `max-w-4xl` / `max-w-5xl` to `max-w-7xl`. See deviation 2.
3. **`PageContainer` renders `<main>`, not `<div>`.** Every route has exactly one content region, so the primitive is the route's landmark. This makes "exactly one content container per route" a DOM-level, role-queryable assertion (`getAllByRole('main')`) rather than a class-string grep. `App.tsx`'s editor route consequently loses its hand-written `<main className="max-w-7xl …">` — `PageContainer` replaces it, and the `brewThisError` banner (today in its own separate `max-w-7xl` wrapper above `<main>`) moves inside it.
4. **The scale modal and any other `fixed inset-0` overlay stay outside `PageContainer`.** `App.tsx`'s `showScaleModal` block remains a sibling of `PageContainer` inside the route's flex column, unchanged in markup. An overlay is not page content and must not inherit the container's width.
5. **Pages that own their `TopBar` must render it in every state, including loading and error.** `App.tsx` stops rendering `TopBar` for `list`, `batches` and `batchDetail`; those pages render it themselves. `BatchDetail.tsx` has two early returns (`error` at :238, `!batch` at :239) and `BatchList.tsx` has one (`error` at :28-30) that today return a bare `<div>`. Each of those early returns must render the route's `TopBar` **and** a `PageContainer` holding the existing message text, or the shell would lose its header entirely in exactly the states where a user most needs the back control. AC-30/AC-31/AC-32 test this.
6. **The sole-`<h1>`-per-route invariant from M5.5_P1 is preserved and its two-route exception is retired.** After this phase, `TopBar`'s `title` is the sole `<h1>` on **all seven** routes: `BatchList.tsx`'s own `<h1>Brewing Batches</h1>` and `BatchDetail.tsx`'s own `<h1>{batch.name}…</h1>` are deleted, and the same strings are passed as `TopBar`'s `title` from inside those same components (so no batch state is lifted into `App.tsx` — M5.5_P1 deviation-entry 7's rationale still holds and is still honoured). `App.test.tsx`'s existing `ROUTE_H1` table and its AC-14 blocks therefore keep asserting the same accessible names and **must pass with their assertions unchanged**; only the two `it(...)` titles that say "owned by BatchList/BatchDetail itself (no TopBar title)" become factually stale, and renaming those two titles is the single permitted rename in that file (AC-27).
7. **`batchDetail`'s status badge moves into `TopBar`'s action slot, not into the title.** Today the badge is a `<span>` nested inside the `<h1>`, which is why `App.test.tsx` matches the heading by regex rather than exact name. Nesting it inside `TopBar`'s `title` is impossible — `title` is `string`, not `ReactNode`, and widening it is out of scope. The badge is therefore rendered as the first child of `TopBar`'s `children`, before `Edit Batch`, with its existing `STATUS_BADGE_CLASS[batch.status]` classes verbatim. The existing regex heading assertion still passes (the name is now exactly `batch.name`, which the regex still matches).
8. **`BatchList`'s `onBack` prop is deleted outright; the three managers' `onBack` is kept.** `App.tsx` passes `onBack={() => setView('list')}` to `BatchList` — behaviourally identical to the sidebar's own `Recipes` button, i.e. pure redundancy, and the concrete instance BUG-005 names. It is removed, along with the prop from `BatchListProps`. The three managers' `onBack` is **not** removed, because `leaveEquipment` / `leaveMashProfiles` / `leaveFermentationProfiles` return to the *open recipe editor* when one exists (`App.tsx:118-135`) — a destination the sidebar cannot reach. Removing it would be a functional regression disguised as a consistency fix. See deviation 5.
9. **`search` is a slot, not a search implementation.** `TopBar` renders whatever node it is given; it owns no query state, no debounce, no placeholder text and no icon. `RecipeLibrary` keeps `query`, `setQuery`, the 200 ms `setTimeout` debounce and the `load(query)` effect **byte-identical in behaviour** — only the JSX location of the input changes.
10. **Falsy slots render nothing.** `search`, like `children`, is guarded by truthiness: `undefined`, `null` and `false` all render **no** slot wrapper, so no `[data-testid="topbar-search"]` element exists in the DOM on the six routes that pass no search. This matches `children`'s existing behaviour exactly and is asserted by AC-11.
11. **Scope guardrail uses a SHA-256 content manifest, not `git diff`.** This repo has exactly **one** commit (`7d88e64`), which predates M1 and contains none of the M1–M5.5 work; `git diff --name-only <base>` against it reports essentially the entire tree and is worthless as a scope check. The executor must therefore capture `git ls-files -co --exclude-standard -z | xargs -0 sha256sum` **before its first edit** and again at the end, and diff the two manifests. This is the same mechanism M5.5_P1's AC-33 and M5.5_P2's AC-25 established, restated here because it is a recurring trap. AC-34 is written against the manifest, not against `git diff`.
12. **No new theme token.** `PAGE_CONTAINER_CLASS` is composed entirely of stock Tailwind spacing/width utilities already used in this codebase (`mx-auto`, `w-full`, `max-w-7xl`, `px-4`, `sm:px-6`, `lg:px-8`, `py-6`). No colour, no custom value, no `tailwind.config` change, no new dependency.

## 2. Component Contracts

### 2.1 Pure-logic contract — `PAGE_CONTAINER_CLASS`

```
export const PAGE_CONTAINER_CLASS: string
```

Its value is exactly, character for character:

```
mx-auto w-full max-w-7xl px-4 sm:px-6 lg:px-8 py-6
```

Binding properties:

- It is a module-level `const` with **no** parameters, no interpolation and no conditional composition. There is no "no-match" or degenerate input case, because there is no input.
- Nothing else in `apps/web/src` may hard-code a `max-w-*` class on a route-level content wrapper after this phase (AC-6 enforces this by source sweep). `max-w-*` on *inner* elements (cards, form field groups, `BatchDetail.tsx:681`'s `max-w-2xl` descriptive paragraph, `TopBar`'s own search-slot cap) is permitted and untouched — the guardrail is specifically about the element that centres a route's content.

### 2.2 Component contract — `PageContainer`

```
export interface PageContainerProps {
  children: ReactNode;
}
export function PageContainer(props: PageContainerProps): JSX.Element
```

- Renders exactly one element: `<main data-testid="page-container" className={PAGE_CONTAINER_CLASS}>{children}</main>`.
- **No `className` prop, no `width`/`variant`/`size` prop, no `as` prop, no rest-spread of extra DOM attributes.** A caller cannot alter the container's geometry. This is the whole point of the primitive (Resolved Ambiguity 2).
- `children` is required. `children={null}` renders an empty `<main>` with the same classes — it never returns `null` and never omits the landmark, because a route with no content must still occupy the same column.
- The component holds no state, no effect, no context, and performs no navigation.

### 2.3 Modified component contract — `TopBar`

```
export interface TopBarProps {
  title?: string;
  leading?: ReactNode;
  search?: ReactNode;   // NEW
  children?: ReactNode;
}
```

**Render structure, in DOM order, inside the existing `<header>` → inner flex `<div>`:**

1. `<div data-testid="topbar-lead" className="flex items-center gap-3 min-w-0">` — `{leading}` then the conditional `<h1>`. Existing markup, classes and the `title !== undefined` guard are unchanged; only the `data-testid` is added.
2. `{search && <div data-testid="topbar-search" className="flex-1 min-w-0 max-w-md">{search}</div>}` — **new**. Rendered **only** when `search` is truthy, using the same truthiness guard shape `children` already uses. When absent, no element bearing `data-testid="topbar-search"` exists in the DOM.
3. `{children && <div data-testid="topbar-actions" className="flex items-center gap-3">{children}</div>}` — existing block, `data-testid` added, classes and guard unchanged.

**Binding constraints:**

- `search` renders **between** the lead group and the actions group in DOM order, on every route that passes it. This is the "designated slot" AC-9 and AC-14 test against.
- `TopBar` owns no query state, no debounce, no icon and no placeholder for the search slot; it renders the node it is handed (Resolved Ambiguity 9).
- The `<header>` element's own classes (`bg-slate-900 border-b border-slate-800 sticky top-0 z-30 h-16 shadow-md`) and the inner flex `<div>`'s classes are **unchanged**. Adding the search slot must not change the bar's height, stickiness or z-index.
- `title` stays `string | undefined` and stays the sole `<h1>` source. It is **not** widened to `ReactNode` (Resolved Ambiguity 7).
- All four props remain optional; `<TopBar />` with no props remains legal and renders the bar with no heading and no slots.

## 5. Deviation Register

Each entry is a judgment call made by this spec, stated with its reasoning and an explicit overrule path for the halt gate.

1. **`TopBarProps` is extended with a `search` slot — a file both M5.5_P1 and M5.5_P2 declared Untouched.** *Reasoning:* BUG-005's expected-behaviour list explicitly names "Search & Filters: standardized placement" as a distinct slot alongside title and action. Folding search into `children` would put it in the right-aligned action cluster with no distinct layout role, no way to give it `flex-1` growth, and — decisively — no way to write AC-14 as "renders inside the designated slot" rather than "renders somewhere in the bar". The prop is **optional and purely additive**, so every existing call site (including all six built by M5.5_P2) compiles and behaves unchanged, and `TopBar` gains no state, no route knowledge and no search logic. *Overrule path:* drop the `search` prop, pass the input through `children` ahead of the action button, and weaken AC-9/AC-14 to "the input is a descendant of the `<header>`" — cheaper, but it makes "consistent search placement" unverifiable, which is half of what BUG-005 asks for.
2. **A single container width, `max-w-7xl`, with no variants — the three profile forms and the batch detail widen.** *Reasoning:* `max-w-7xl` is already what the two densest routes (recipe library grid, recipe editor) use; narrowing them would regress real content. Widening the forms and the batch detail is the lesser cost, and a two-tier scale ("wide for lists, narrow for forms") is precisely the mechanism that generated BUG-005 — a primitive that can express two widths will express five within a milestone. The single-value, no-props design makes the inconsistent case unrepresentable. *Risk acknowledged:* a single-column form at 1600 px will read sparse. *Overrule path:* add `variant?: 'default' | 'narrow'` to `PageContainerProps` with a second frozen constant, apply `narrow` to the three forms only, and amend AC-5 to "the set of distinct container classes has size ≤ 2, and each route's value matches the table in §2.4."
3. **`PageContainer` renders `<main>`, replacing `App.tsx`'s hand-written editor `<main>`.** *Reasoning:* it makes AC-4 a landmark-role assertion instead of a class-string grep, and guarantees exactly one main landmark per route (an accessibility improvement that falls out for free). *Overrule path:* render a `<div>` and drop the `getAllByRole('main')` half of AC-4, keeping the testid half.
4. **`BatchDetail`'s edit-mode `Cancel` / `Save Measurements` footer stays in the body.** *Reasoning:* `Save Measurements` is a `type="submit"` inside an 838-line component's `<form onSubmit={handleSave}>`; moving it to `TopBar` requires the `form={id}` association plumbing M5.5_P2 used, applied to a far larger file with four independent error states, for a control BUG-005 never names. The bug's complaint about this route is the redundant `← Back` and the ad-hoc header — both fully closed here. *Consequence, stated plainly:* after this phase the batch-edit view is the one place in the app where a Save action is not in the top bar. *Overrule path:* extend §1.2's `BatchDetail.tsx` row to permit adding `id="batch-edit-form"` to the `<form>` and moving both footer buttons into `TopBar`'s `children` with `form="batch-edit-form"` on the submit button, and add ACs mirroring M5.5_P2's AC set for form association. Recommended as a follow-up `BUGS.md` entry if not taken now.
5. **The three managers keep their `leading` back arrow, while `list` and `batches` have none.** *Reasoning:* the managers' `onBack` calls `leaveEquipment`/`leaveMashProfiles`/`leaveFermentationProfiles`, which return to the **open recipe editor** when one exists — a destination the sidebar cannot reach. `BatchList`'s `onBack` merely called `setView('list')`, duplicating the sidebar's `Recipes` button, so it is deleted. *Consequence:* a residual asymmetry remains — three of five top-level nav destinations show a back arrow. It is defended as functional, not decorative, and the "no back control in a page **body**" rule (AC-23) is uniform regardless. *Overrule path:* delete `onBack` from all three managers and from their `App.tsx` call sites, accepting the loss of return-to-editor; this would also require deleting `leaveEquipment`/`leaveMashProfiles`/`leaveFermentationProfiles` and amending §2.4.
6. **No empty/error-state redesign.** BUG-005's expected-behaviour list mentions "standardized empty/error states inspired by Brewfather's streamlined density." This phase re-homes existing empty/error markup into the shared container **without restyling it** — the empty-state cards, error panels and `Retry` buttons keep their current copy and classes. *Reasoning:* restyling them is a visual-design task with no binary acceptance criterion available ("streamlined density" is not testable), and mixing it into a structural refactor would make the manifest diff and the preserved-test guarantees much harder to reason about. *Overrule path:* a separate follow-up phase with concrete per-state mockups to test against.
7. **`RecipeLibrary` gains a `notices` passthrough prop rather than `App.tsx` keeping a `TopBar`.** *Reasoning:* `App.tsx` owns three banners that today render between its `TopBar` and `<RecipeLibrary />`. Once `RecipeLibrary` renders the `TopBar` itself (the M5.5_P2 pattern), those banners would end up **above** the bar. `notices` is the minimal fix: a presentation-only `ReactNode` passthrough that leaves every banner's state, condition and markup in `App.tsx`. *Rejected alternative:* keeping `TopBar` in `App.tsx` for the `list` route and lifting `query` state out of `RecipeLibrary` — that would break the existing standalone `RecipeLibrary.test.tsx` render sites and contradict the pattern the other six routes now follow. *Overrule path:* move the three banners' JSX into `RecipeLibrary` outright and drop the prop, at the cost of moving `libraryError`/`equipmentError` ownership out of `App.tsx`.
8. **Full BUG-005 scope accepted: 18 files.** Stated up front rather than discovered at execution. *Reasoning:* in Resolved Ambiguity 1. *Overrule path:* split into P3a (`PageContainer` + the seven containers) and P3b (`TopBar` search slot + `RecipeLibrary`/`BatchList`/`BatchDetail` chrome moves); the ACs partition cleanly along AC-1..AC-7/AC-22 versus AC-8..AC-33, though AC-13's "one `TopBar` per route" only becomes true after P3b.
