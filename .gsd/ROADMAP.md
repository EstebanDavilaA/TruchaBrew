# ROADMAP: TruchaBrew

## Executive Summary & Product Vision

A self-hosted, single-user replacement for Brewfather: design a recipe, trust the numbers, brew it, and log the batch end-to-end in your own tool, on your own machine, with your own data. No cloud, no subscription, no community library.

**MVP bar (from `.gsd/DISCOVERY.md`):** one full brew day for a single recipe, planned and logged end-to-end through `Planning → Brewing → Fermenting → Conditioning → Completed`, with calculated numbers that match the known-good Brewfather exports in `.gsd/documents/montano_brewing_recipes.json`, persisted in SQLite so nothing is lost on refresh. Inventory deduction and cost rollup are explicitly **not** MVP. Desk/laptop only — no mobile-first UI, no offline tolerance.

**MVP is complete at the end of Milestone 5.** Milestones 6–9 are post-MVP.

## Starting position (from the codebase audit — ground truth, not re-derived here)

- Builds and lints clean; dev server runs. **Zero tests, no test runner.** No stabilization milestone needed.
- Real, working code to extend — not scaffolding to throw away: `src/calculations/brewingMath.ts` (OG/color/ABV already accurate against the fixture; IBU materially off), `src/types/brewing.ts`, a functioning in-memory recipe designer (`src/App.tsx` + `src/components/*Section.tsx`, `StatsHeader.tsx`), `src/data/seedData.ts`, `src/utils/srmColor.ts`.
- **No persistence layer of any kind.** A page refresh loses everything. This — not the calculations — is the single largest gap between today and the MVP bar.

## Sequencing rationale vs. the build spec's reference order

The build spec's step order (calc → config → profiles → recipes → inventory → batches → tools → BeerXML) was written before the codebase existed and is a **layer/feature checklist, not a slice sequence**. The user confirmed keeping it as a *reference*. Three deliberate departures:

1. **Recipes move ahead of Config and Profiles.** Recipes already exist and work; what they lack is persistence. Building Config first would mean writing settings for a thing that can't yet be saved. Config becomes a real slice only once there is stored data whose display it changes (M7).
2. **Profiles are split.** Equipment/Mash/Fermentation profiles (M3) are pre-MVP because they drive brew-day numbers. Water profiles + chemistry (M6) are post-MVP because the MVP bar doesn't require them.
3. **Inventory moves to last (M9)**, per the discovery answer that deducts/cost are deferred past MVP. Batches are therefore built in M4/M5 *without* the inventory-checkoff path, and M9 adds it to the existing batch slice rather than the batch slice waiting on it.

## Structural decision: when to split the flat `src/` into the monorepo layout

**Decision: split in Milestone 1, scoped to `/packages/calculations`, `/packages/shared-types`, and `/apps/web` only. `/apps/api` is not created until Milestone 2, when it has something to serve.**

Reasoning — the audit offered two defensible triggers, (a) when the calc engine first gets a real test suite, or (b) deferred to the persistence milestone:

- Trigger (a) is chosen because M1 is the only milestone that touches nothing but calculations and their display. The move is mechanical (current folders map ~1:1 onto target packages) and its blast radius is at its lifetime minimum right now — every subsequent milestone adds files that would have to move too.
- Deferring to (b) would land a whole-repo mechanical refactor *inside* the riskiest milestone (first backend, first ORM, first DB). If M2 then fails verification, `/diagnose` can't cleanly separate "the persistence design is wrong" from "the refactor broke an import path." Keeping the refactor in the quiet milestone keeps M2 diagnosable.
- M1 must stand up a test runner and a build config anyway. Doing that once, in the target package layout, avoids configuring vitest twice.

The split is scaffolding carried **inside** M1's slice, not a milestone of its own — a pure-refactor milestone would have no user-visible outcome and is exactly the anti-pattern this roadmap rejects.

## Decoupled Milestones

### Milestone 1: Numbers I can trust
- **User-visible outcome:** Open any of the six Montano recipes in the designer and the displayed OG, FG, ABV, IBU, colour, BU:GU and RBR match what Brewfather calculated for that same recipe — including the efficiency and attenuation figures, which today are hardcoded lies on screen.
- **Builds on:** none — first slice. Extends the existing `src/calculations/brewingMath.ts` and `StatsHeader.tsx`; does not rewrite them.
- **Estimated phases:** 1 (delivered as 1 — M1_P1)
- **Hardening scope:**
  - Stand up vitest (no test runner exists today) and drive the calc engine from all six fixture recipes in `.gsd/documents/montano_brewing_recipes.json` as parameterised known-good cases.
  - Close the three IBU calibration bugs: hardcoded `*1.1` pellet bump replaced by the Equipment profile's `hopUtilization%`; `'Aroma'`/hopstand additions given reduced hopstand utilisation instead of falling through to full-boil (only `'Whirlpool'` is special-cased today); wort-gravity basis corrected away from raw `preBoilGravity`.
  - Fix the MCU bug that passes SRM into a slot expecting Lovibond (systematic colour bias).
  - Wire `brewhouseEfficiencyPct` into the calculation path (currently defined on the type but unused — only `mashEfficiencyPct` drives OG), and make `StatsHeader.tsx` read efficiency and attenuation from actual recipe/equipment/yeast data instead of the string literals `Efficiency: 75%` / `Attenuation: 78%`.
  - Perform the `/packages/calculations` + `/packages/shared-types` + `/apps/web` split per the decision above. Delete the dead Vite-template leftovers (`App.css`, template SVG/PNG assets) while moving.
- **Verification threshold:** For all six fixture recipes, calculated OG, FG, ABV, SRM/EBC, BU:GU and RBR are within 1% of the fixture's recorded value and IBU within 1.5 IBU absolute (the currently-failing case, 21.0 vs 13, must land inside that band). `pnpm test` runs from a cold clone; `tsc` and the web build still exit 0; the running app displays those same numbers — a passing test suite alone does not satisfy this milestone.

### Milestone 2: A recipe library that survives a refresh
- **User-visible outcome:** Create a recipe, name it, close the browser, come back, and it's still there — plus a list of all saved recipes to search, open, rename, duplicate, and delete.
- **Builds on:** Milestone 1 (calculations are trustworthy before anything is stored against them).
- **Estimated phases:** 1 (delivered as 1 — M2_P1)
- **Hardening scope:**

Equipment profiles and the `seedData.ts` ingredient list migrate from static TS constants to seeded DB rows so a stored recipe's `equipmentId` still resolves after reload.
  - Replace the designer's `useState`-only model with load/save against the API. Recipe stats stay locally recalculated for live editing — the DB stores inputs, and derived `RecipeData` is a cache, never the source of truth.
  - Add the Misc (water agent/fining/spice) ingredient section, absent from `src/types/brewing.ts` today, so the stored recipe shape isn't missing a category that batches will later snapshot.
  - Fix `handleScaleRecipe`: it currently rescales ingredient amounts but not boil-off and trub/chiller loss, so scaling does not actually preserve gravity and IBU as promised. Scale must recompute water volumes from the equipment profile.

- **Verification threshold:** A recipe entered through the UI is recoverable byte-identical (same ingredients, same profile reference, same computed stats) after a full app restart and a fresh DB read. A recipe scaled from 20 L to 40 L reproduces its original OG and IBU within the M1 tolerance bands. Deleting a recipe leaves no orphaned ingredient rows.

### Milestone 4: Brew this recipe, log the brew day (Completed)
- **User-visible outcome:** Hit "Brew this" on a recipe and get a Batch that freezes the recipe exactly as brewed; walk it from Planning into Brewing and record what actually happened — measured pre-boil gravity, mash pH, actual volumes and boil time — and see measured-vs-estimated side by side.
- **Builds on:** Milestone 3 (a batch snapshot is only meaningful once the recipe carries real equipment and mash data).
- **Estimated phases:** 1 (delivered as 1 — M4_P1)
- **Hardening scope:**
  - Batch entity per build-spec §2, stored as a **frozen snapshot** of the recipe, not a live foreign key — later edits to the source recipe must not retroactively alter a brewed batch. This is the single most important correctness property of the milestone.
  - Batch list, batch number assignment, brew date, and the status pipeline with `Planning → Brewing` transitions plus timestamped `BatchNote` entries.
  - Measured-field capture and the mash-efficiency calculation from build-spec §3.9, computed from measured pre-boil gravity against the snapshot's grain bill.

- **Verification threshold:** Create a batch from a recipe, then edit that recipe's grain bill — the batch's snapshot is provably unchanged (asserted in a test, not eyeballed). Entering a measured pre-boil gravity produces a measured efficiency that a hand-calculation from the fixture data confirms. Status cannot skip or reverse pipeline stages except through an explicit, deliberate action.

## Initiative: Experience Redesign (Milestones 23–28)

**Source:** `.gsd/DISCOVERY.md` (Experience Redesign), an external UX/IA/accessibility/design-system audit of `apps/web`, and a `codebase-mapper` verification pass of that audit against the actual source (2026-08-20). Where audit and mapper disagreed, the mapper's findings are treated as ground truth.

**Starting position:** all four Layer 1 gates green on the pre-existing tree (typecheck / lint / build / test, 1731 passing across 113 files). **No stabilization milestone is needed** — this initiative starts from a working app and makes it coherent, it does not repair a broken one.

**Scope framing (from the answered discovery questions):** all four goals — visual consistency, WCAG accessibility, mobile usability, IA clarity — are pursued together with no stated priority; there is **no rebrand** (the job is to make the *existing* look and patterns coherent, not to invent a new one); routing is deliberately **not** the first milestone; naming standardizes on **"Profile"**, not "Schedule"; the audit's six "quick win" items are **folded into the first milestone** rather than being taken under the lightweight-task exception; and there is no deadline forcing items out of scope.

**Sequencing rationale — three deliberate decisions:**

1. **Quick wins are a milestone, not a rounding error.** Items 1–6 are individually small, but together they are the difference between "some dialogs are accessible" and "every dialog is." Bundled, they form a single coherent user-visible outcome ("nothing in this app is visibly second-class anymore") that is verifiable as a whole. Taken separately under the lightweight-task exception, six unrelated small edits would leave no single moment where that claim becomes true — which is exactly the user's stated reason for folding them in.
2. **Routing lands late, and it absorbs the third `window.confirm()`.** The audit called routing the highest-leverage item; the user explicitly declined to sequence it first. That is the right call here for a structural reason the audit missed: `App.tsx:144`'s `confirmLeaveEditorIfDirty` is the app's *only* navigation guard, and it cannot be swapped for `ConfirmDialog` (it needs a synchronous decision). It should be rebuilt on the router's blocker API when routing lands — so it belongs to the routing milestone, not to the quick-wins milestone that fixes the *other* two `window.confirm()` calls.
3. **The Modal wrapper and the router are never in the same milestone.** Both land heavily in `App.tsx` (770 lines) and `BatchDetail.tsx` (1224 lines, the app's most fragile file). Sequencing them together would make any failure undiagnosable — `/diagnose` could not separate "the focus trap is wrong" from "the route boundary is wrong." They are Milestone 25 and Milestone 27, with the mobile-sidebar slice deliberately between them.

**Two structural constraints every milestone below must respect** (both found by the mapper, both invisible in the raw audit):

- `apps/web/test/designSystem.test.ts` asserts that the `designSystem` module exports **no functions, components, or hooks**, and pins all 17 existing token strings by exact equality. The shared `Modal` component and any a11y hook must therefore live in a **new** module; any token *string* change must update that test in the same commit.
- `apps/web/test/accessibilityAndPolish.test.tsx:208-214` (AC-11) asserts textually on `App.tsx:761`'s inline scale modal — the **7th** dialog the audit didn't count. Migrating it onto the shared wrapper must reconcile with that assertion rather than break it.

## Initiative: Living Design System (Milestones 30–35)

**Source:** the user's report that the app "still looks patchwork" after the Experience Redesign initiative, an external design-system brief proposing a `components/ui/` primitive layer, and a `codebase-mapper` verification pass of both against the actual source (2026-08-24). Every number below was read out of the tree, not inferred from the brief.

**Starting position:** all four Layer 1 gates green on the pre-existing tree — `npm run typecheck` exit 0 (4/4 workspaces), `npm run build` exit 0 (vite 8.2.0, 1887 modules, 2.14s, only the pre-existing >500 kB chunk-size warning), `npm run lint` exit 0 (oxlint, 4 pre-existing `only-export-components` warnings), `npm test` exit 0 at **1,970 passing / 2 skipped across 119 files** (web 930, calculations 602, api 438). **No stabilization milestone is needed.** This initiative starts from a fully working, verification-clean app and makes it coherent; it does not repair it.

### The diagnosis — this is a deferred item finally being scheduled, not a repair of failed work

Milestones 23–28 did not fail at what they scoped. **The patchwork the user sees is precisely the scope those milestones explicitly deferred, and this roadmap predicted this exact moment.** Milestone 24's hardening scope states that its sweep targets only "the ~13–20 files carrying real local duplicates … **not** full-app token coverage," and logs raising coverage to 100% to *Deferred / not scheduled* — whose bullet closes: *"Slot it at a future `/steer` if the drift keeps recurring."* The drift kept recurring. This initiative is that bullet being claimed.

There is a second, sharper mechanism worth naming, because it explains why the `/steer` critic audits never caught the drift:

1. **M24's guardrail test was written against the wrong unit.** `apps/web/test/designTokens.test.ts` AC-12 bans local *named constants* via `/^\s*(export\s+)?const\s+[A-Z_]*(BUTTON|INPUT|SELECT)[A-Z_]*_CLASS\s*=/m`. It passes today. But the actual drift does not live in named constants — it lives in (a) inline `className="…"` string literals and (b) `${TOKEN} extra classes` template-literal overrides. Neither is visible to that regex. **The guardrail is green while the app is inconsistent.**
2. **The token tests verify the vocabulary's *contents*, never its *adoption*.** `designSystem.test.ts` pins every token's exact string value; nothing asserts that any component uses it. Proof: **`BUTTON_ICON_CLASS` and `BODY_TEXT_CLASS` have zero consumers app-wide** — both defined, both pinned by exact-string assertions, both dead — while 15+ hand-rolled icon buttons exist alongside them.
3. **The architectural lesson to encode:** a token is *a string you may choose to use*; a component is *a boundary you must go through*. The one place this codebase already got consistency right is `Modal.tsx` (M25_P1), and it worked precisely because it pairs a component boundary with an **adoption test** — `ScopeGuardrail.test.tsx` AC-4 asserts all 8 dialogs import and render `<Modal>`. **Every milestone below must ship an adoption assertion, not just a value assertion.** That is the mechanism change; the migrations are the visible consequence.

|---|---|---|---|
| input | 126 | 92 (74%) | 32 |
| select | 32 | 29 (91%) | 3 |
| textarea | 6 | 6 (100%) | 0 |
| **button** | **150** | **56 (37%)** | **94** |

Buttons therefore range 32–40 px beside 38 px inputs, and **no token declares a height.** Eight sites use `!important` (`!px-3 !py-1.5`, `!p-0`, `!pl-9`) to fight this — proof the token's geometry is wrong for the job and no size variant exists.

### How the external brief maps to reality

The brief proposes `FormField`, `Input`, `NumberInput`, `Select`, `Textarea`, `Button`, `Card`, `MetricTile`, `Badge`, `Table` exported via `ui/index.ts`, with `designSystem.ts` kept constants-only. The user was explicit that **nothing in it is locked in.** Verdict:

- **Well-justified by the evidence:** `FormField` (112 labels / 20 variants + 78 unnamed controls), `NumberInput` (63 sites / 9 variants), `Button` (94 raw / 71 variants — the single biggest win), `Input`, `Select`.
- **Already substantially exists; scope as *extend*, not *build*:** `Card` (= `CARD_CLASS`, 57 uses), `MetricTile` (`METRIC_TILE_CLASS`/`METRIC_LABEL_CLASS`/`METRIC_VALUE_CLASS`, 34–36 uses each), `Badge` (`STATUS_BADGE_*`, already a typed `Record<BatchStatus, string>` and exhaustive over the union). **`designSystem.ts` itself is good and must not be rebuilt** — 107 lines, 26 exports, strictly constants-only; its `CARD_CLASS` is byte-identical to what the brief proposes and `MONO_VALUE_CLASS` is already exactly `font-mono tabular-nums tracking-tight`. ### Structural constraints every milestone below must respect

These are migration hazards that will otherwise fail Layer 1 for reasons unrelated to correctness:

1. **`apps/web/test/designSystem.test.ts` pins every token's exact string value.** Changing `INPUT_CLASS` (to add a height, or to remove `focus:outline-none`) breaks it. It updates in the same commit as any token change.
2. **`designTokens.test.ts` AC-7 asserts `Object.keys(designSystem)` has length exactly 26 and matches an exact name list.** Adding *any* token fails it. Every milestone that adds a token updates that list.
3. **`designTokens.test.ts` carries occurrence-*count* assertions a migration necessarily breaks** — AC-19 pins `placeholder-slate-500` at exactly 4, AC-20 pins `text-slate-600` at exactly 13, AC-21 pins `border-slate-500/30` at exactly 1, AC-18 pins `text-slate-500` at 0. Collapsing N call sites into one primitive changes these counts by construction. **Converting count-pinned assertions into adoption/invariant assertions is in-scope work inside each migration milestone** — it is the mechanism by which the guardrail starts measuring the right thing, not incidental test churn.
4. **`designTokens.test.ts` AC-13 pins that 7 named files import specific tokens** (`PostBrewCalibrationModal`, `ReadingLog`, `RecipeImportModal`, `SensoryEvaluationPanel`, `SplitPackagingPanel`, `WaterCalculatorModal`, `pages/BatchDetail`). Migrating any of them from `className={INPUT_CLASS}` to `<Input>` removes that import and fails the test. Each row converts to an adoption assertion in the milestone that migrates its file.
5. **`designSystem.test.ts` asserts the module exports no functions, components or hooks.** The new `components/ui/` primitives live in their own modules — never inside `designSystem.ts`. This is the same constraint that forced `Modal.tsx` into a new module in M25.
6. **No class-merging dependency is installed** — `clsx`, `tailwind-merge`, `class-variance-authority` and `tailwind-variants` are all absent. Installed: React 19.2.8, Tailwind 4.3.3 (`@tailwindcss/vite`), react-router 7, lucide-react 1.28.0, vitest 3.2.4, @testing-library/react 16.1.0. Naive string concatenation cannot resolve Tailwind conflicts like `px-3` vs `!px-3` — which is exactly why 8 sites currently use `!important`. Whether to add a dependency or to design the variant API so overrides are unnecessary is a real `/plan` decision, deliberately not made here.
7. **Migration risk is lower than it looks:** the behavioural suite is only weakly coupled to markup — just 6 `toHaveClass` assertions in 1 file, and 9 test files import `designSystem`. Most tests query by role or text. Migrating a screen mostly does *not* churn its behavioural tests; the coupling is concentrated in the two token test files above.
8. **`ScopeGuardrail.test.tsx` and `accessibilityAndPolish.test.tsx` carry cross-file source sweeps** from M23/M25 (dialog-wrapper adoption, `window.confirm` bans, deleted-file assertions). Migrations reconcile with them rather than break them.

### Sequencing rationale

Milestones are sequenced by **user-facing surface**, never by layer. "Build the primitive layer" followed by "migrate the consumers" is explicitly forbidden here — it is the exact horizontal-layer anti-pattern that produced the current situation, where a vocabulary exists and two of its words have no speakers. Each milestone ships the primitives *its own surface needs* and migrates that surface in the same slice, so at the end of every milestone a brewer can open a specific screen and see it is more consistent. Later milestones **extend** the primitive layer with new axes (`size`, `align`, icon slot, `Table`, `Badge`) rather than rebuilding it — which is what keeps them decoupled: nothing in Milestone 33 requires reopening Milestone 30's calculator slice, because a new prop is additive to the primitive and invisible to existing call sites.

Three specific orderings are deliberate: the **calculators hub goes first** because it already has a component boundary (`CalculatorCard.tsx`'s `NumericField`/`SelectField`), so migrating it is a re-point rather than a rewrite — lowest blast radius, highest signal. The **focus-ring fix rides with that first form-control migration** rather than becoming a standalone "accessibility" milestone, which would be a horizontal layer. And the **guardrail rewrite lands last, paired with a real surface** (tables and badges), because a guardrail written before the migrations would be a guardrail written against the code that exists rather than the code that should.
