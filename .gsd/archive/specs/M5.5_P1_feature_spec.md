# FEATURE SPECIFICATION: M5.5_P1 — A shell that scales past six buttons

> **Milestone 5.5, Phase 1.** First post-MVP phase. Pure UX rework of already-shipped surfaces.
> Closes **BUG-002** (sidebar navigation / contextual top bar) and **BUG-003 Option B** (batch phase stepper).
> **Zero** API, schema, migration, or `packages/calculations` work. If execution discovers it needs any of those, that is a **deviation** to raise at a halt, not a change to make.

---

## Phase Summary

The application shell currently repeats a single 64px top bar on every route, and that bar carries *both* the app's destination links (Equipment Profiles, Mash Schedules, Fermentation Schedules, Batches — plus Scale Batch / Brew This / Save on the editor route) *and* the current page's contextual actions. There is no direct link to the recipe library at all (BUG-002's original report). At six buttons the row is already full; Milestones 6–9 add more destinations.

This phase splits the two concerns apart:

- **Destinations** move into a persistent left **Sidebar** that renders on every route, carrying five links: Recipes, Equipment Profiles, Mash Schedules, Fermentation Schedules, Batches. It has a collapse toggle that shrinks it to an **icon-only rail** (never to zero width — see Resolved Ambiguities). Collapse state is React state lifted above the route switch, so it survives navigation within a session; it is *not* persisted across a page reload, and no requirement in this spec asks for that.
- **Contextual actions** stay in a **TopBar** that renders only the current page's title plus that page's own action controls. On the editor route those actions are exactly the ones that are contextual to editing a recipe — Scale Batch, Brew This, and the `SaveBar` — and the destination buttons are gone from it.

Separately, `BatchDetail.tsx`'s edit-mode status control — today a bare `<select>` populated from `allowedNextStatuses(batch.status)` — is replaced by an explicit **BatchStepper**: a visual five-step indicator (Planning → Brewing → Fermenting → Conditioning → Completed) rendering done / active / upcoming state, with a single explicitly-labelled forward transition button ("Advance to Brewing", "Start Fermentation", "Move to Conditioning", "Mark Completed") driven by **the same** `allowedNextStatuses` function. The state machine in `packages/calculations/src/batchPipeline.ts` is **not touched** — it is already verified by M4_P1 and M5_P2 and this phase changes only how it is surfaced.

### Key Behaviors

1. Every route that today shows the destination-button row instead shows a Sidebar carrying all five destinations, and a TopBar carrying only that route's title and contextual actions.
2. The Sidebar's collapse toggle switches between an expanded (labels + icons) and a collapsed (icons only) rail. **Every destination remains present and clickable in the collapsed state** — collapsing never removes a route from reach.
3. Collapse state lives in one place, above the route switch, so navigating from any route to any other preserves it.
4. Navigating to the Recipes destination from the editor route still runs the existing unsaved-changes confirm; navigating to any other destination still does not. That asymmetry is pre-existing behavior (App.tsx §2.5 comments) and this phase preserves it exactly.
5. `BatchDetail.tsx`'s edit form contains no `<select>` for status and no control labelled "Status". The stepper offers exactly the forward transitions `allowedNextStatuses` allows and nothing else; from `Completed` it offers none.
6. Choosing a transition marks it **pending** and mutates only `formData.status`. Nothing is written to the server until the existing "Save Measurements" submit fires, and the existing `updateBatch` call, its payload shape, and its error handling are unchanged.
7. Everything else on the batch page — the measurement inputs, `MeasuredComparison`, `CarbonationPanel`, `ReadingLog`, `FermentationChart`, `BatchNoteLog`, the taste fields — is untouched and remains one flat, non-phase-scoped form. This is BUG-003 **Option B**; Option A (per-phase field grouping, phase-scoped measured-vs-estimated panels) is deliberately **out of scope**.

### Resolved Ambiguities (Binding)

- **Collapsed representation is an icon-only rail, never zero-width.** Collapsed the sidebar is `w-16` (64px) and still renders all five destination buttons as icon-only controls plus the toggle. It is **not** hidden, not translated off-canvas, and not unmounted. Rationale: the roadmap's verification threshold requires that "every route reachable from the old top-bar destination buttons is still reachable via the sidebar, with the collapse/hide toggle provably not losing navigation state" — a fully-hidden sidebar makes four of five routes unreachable while collapsed unless a floating re-open affordance is also built, which is more surface than this phase wants. Recorded as **deviation-register entry 1**.
- **Expanded width is `w-60` (240px); collapsed width is `w-16` (64px).** These are the only two states. There is no intermediate, no drag-resize, no animation requirement (a CSS transition is permitted but not required and is not an acceptance criterion).
- **Label hiding is by non-render, not by CSS.** In the collapsed state the destination button's text label node **must not be in the DOM** (so `queryByText('Batches')` returns `null`), while the button itself keeps its accessible name via `aria-label` (so `getByRole('button', { name: 'Batches' })` still resolves and is still clickable). `sr-only`, `hidden`, `display:none`, or a zero-width span are all **non-compliant** — a criterion below distinguishes these cases and a CSS-only implementation fails it.
- **Collapse state lives in `AppInner` as `const [sidebarCollapsed, setSidebarCollapsed] = useState(false)`,** declared above every `if (view === ...)` early return. Default is **expanded** (`false`). No `localStorage`, no `sessionStorage`, no URL param, no context. Recorded as **deviation-register entry 2**.
- **Active-destination mapping is total over the seven `View` values.** `list` and `editor` both mark **Recipes** active; `batchDetail` and `batches` both mark **Batches** active; `equipment`, `mashProfiles`, `fermentationProfiles` mark their own item. Exactly one item carries `aria-current="page"` on every route — never zero, never two.
- **`allowedNextStatuses` self-entry is filtered out for button rendering, not for gating.** Every entry in `BATCH_STATUS_TRANSITIONS` includes the status itself (so a measurements-only re-save is legal). The stepper derives its transition targets as `allowedNextStatuses(currentStatus).filter(s => s !== currentStatus)`. For `Completed` that yields `[]`. The self-entry is *not* removed from the calculations table and re-saving without a status change stays legal.
- **Step state is derived from the SERVER's status (`batch.status`), never from the pending selection (`formData.status`).** The done/active/upcoming ring must not lie about what is persisted. The pending selection gets its own separate visual treatment (below).
- **Pending-transition semantics.** When `selectedStatus !== currentStatus`, the stepper (a) applies a distinct pending treatment to the selected step, (b) renders the visible text `Pending — save to apply`, and (c) replaces the forward transition button with a **Cancel transition** button that calls `onSelect(currentStatus)`. When `selectedStatus === currentStatus`, none of (a)/(b)/(c) render and the forward transition button (if any) is present.
- **Degenerate status input.** If `currentStatus` is not a member of `BATCH_STATUSES` (defensively possible only through a corrupted payload; the type system otherwise forbids it), `stepStates` returns all five steps as `upcoming` with **no** step marked `active`, and the transition-target list is `[]` — no button, no crash, no fabricated placeholder step. This mirrors `canTransitionBatchStatus`'s existing defensive `return false`.
- **Step markers are not interactive.** Done and upcoming step markers must not be `<button>`s and must not be focusable. The only interactive elements inside the stepper are the forward transition button and the Cancel transition button. This is what structurally prevents a backward or skipping transition — there is no control to click.
- **Existing in-page back buttons and headings stay.** `EquipmentManager`, `MashProfileManager`, `FermentationProfileManager`, `BatchList` and `BatchDetail` each render their own heading and their own back control today. They are **not** touched by this phase, even though the sidebar makes some of them redundant. Removing them would ripple `onBack` prop removals through five components and roughly forty existing test call sites for no user-visible gain in this phase. Recorded as **deviation-register entry 3**.
- **Duplicate-text repairs are permitted in existing tests, subject-preserving only.** Because the TopBar introduces an `<h1>` whose text may equal a string a page component already renders, an existing `getByText(...)` may become ambiguous. The executor **may** narrow such a query (e.g. to `getByRole('heading', { level: 1, name: ... })` or a scoped `within(...)`) and **may not** change what the assertion asserts, weaken it, skip it, or delete it. Every such repair must be named individually in the handoff.
- **Icon identity is not an acceptance criterion.** Icons come from `lucide-react` (already a dependency). Reuse the four names App.tsx already imports (`Beer`, `Settings`, `Thermometer`, `Snowflake`) where they apply; pick any exported icon for Recipes and for the collapse toggle. If a chosen export name does not exist in the installed version, substitute a different exported icon — no criterion below names an icon.

### 2.2 `TopBar` — `apps/web/src/components/TopBar.tsx`

```ts
export interface TopBarProps {

   * When present, rendered as an <h1> — and on the five routes that pass it, it is the

  /** Optional lead control (e.g. the editor route's back-to-library arrow). */
```

`TopBar` renders **no destination link of any kind** — it has no `onNavigate`, no route knowledge, and no `NavDestination` import. It keeps the existing header chrome: `bg-slate-900 border-b border-slate-800 sticky top-0 z-30`, `h-16`.

**Sole-`<h1>` guarantee and its two named exceptions (binding).** The invariant this phase guarantees is: **on every route, the rendered shell contains exactly one `<h1>` element.** It is *not* "TopBar always owns that `<h1>`". Two routes already have a page-level `<h1>` that §1.3 forbids touching — verified by direct inspection: `apps/web/src/pages/BatchList.tsx:40` renders `<h1 …>Brewing Batches</h1>` and `apps/web/src/pages/BatchDetail.tsx:368` renders `<h1 …>{batch.name}…</h1>`. On those two routes (`batches`, `batchDetail`) `App.tsx` therefore passes **no `title` prop**, TopBar renders no heading, and the page's own pre-existing `<h1>` stands as the shell's sole level-1 heading. On the other five routes (`list`, `editor`, `equipment`, `mashProfiles`, `fermentationProfiles`) TopBar's `title` is the sole `<h1>`. No `role="heading"` / `aria-level` substitute is rendered on the two exception routes — a second element with heading semantics would reintroduce the same ambiguity this carve-out exists to remove.

### 2.3 `BatchStepper` — `apps/web/src/components/BatchStepper.tsx`

**Pure logic (no React, no props, deterministic):**

```ts
export type StepState = 'done' | 'active' | 'upcoming';

export interface StepDescriptor {
  readonly status: BatchStatus;
  readonly state: StepState;
}

/**
 * Total over any input, including values outside the BatchStatus union.
 * Always returns exactly 5 descriptors, in BATCH_STATUSES order.
 * index < currentIndex -> 'done'; index === currentIndex -> 'active'; index > currentIndex -> 'upcoming'.
 * NO-MATCH CONTRACT: when `current` is not in BATCH_STATUSES (currentIndex === -1),
 * every descriptor is 'upcoming' and none is 'active'. Never throws, never returns
 * fewer or more than 5, never fabricates a step.
 */
export function stepStates(current: BatchStatus): readonly StepDescriptor[];

/** Keyed by TARGET status. 'Planning' is never a forward target and has no entry. */
export const TRANSITION_LABEL: Readonly<Record<Exclude<BatchStatus, 'Planning'>, string>>;
```

`TRANSITION_LABEL` values, binding:

| Target status | Label |
|---------------|-------|
| `Brewing` | `Advance to Brewing` |
| `Fermenting` | `Start Fermentation` |
| `Conditioning` | `Move to Conditioning` |
| `Completed` | `Mark Completed` |

**Stateful component:**

```ts
export interface BatchStepperProps {
  /** The persisted server status. Drives step state AND transition gating. */
  currentStatus: BatchStatus;
  /** The pending form selection (BatchDetail's formData.status). */
  selectedStatus: BatchStatus;
  /** Fired with the chosen target. Performs no network call. */
  onSelect: (next: BatchStatus) => void;
  /** Disables the transition and cancel controls (BatchDetail passes isSaving). */
  disabled?: boolean;
}

export function BatchStepper(props: BatchStepperProps): JSX.Element;
```

**Rendering contract:**

1. Five step markers, always, in `BATCH_STATUSES` order, each showing its status name as visible text and its `state` distinguishable via `data-state="done" | "active" | "upcoming"` on the marker element. Markers are **not** buttons and are **not** focusable.
2. Forward targets = `allowedNextStatuses(currentStatus).filter(s => s !== currentStatus)`. This is the **only** call site of `allowedNextStatuses` in `apps/web/src` after this phase.
3. If `selectedStatus === currentStatus`: render one button per forward target, labelled from `TRANSITION_LABEL`, each calling `onSelect(target)`. (The table yields at most one forward target per status, but the implementation must map over the filtered array rather than assuming a single element.)
4. If `selectedStatus !== currentStatus`: render **no** forward transition button; render the text `Pending — save to apply`; render one button named `Cancel transition` calling `onSelect(currentStatus)`; apply a pending visual treatment to the `selectedStatus` step marker via `data-pending="true"` (no other marker carries it).
5. If forward targets is `[]` **and** `selectedStatus === currentStatus` (i.e. `currentStatus === 'Completed'`): render **no** button at all and render the static text `This batch is complete.` No disabled placeholder button, no empty control, no `<select>`.
6. `disabled === true` sets the `disabled` attribute on whichever buttons are rendered. It never changes which buttons are rendered.
7. Theme reuses `STATUS_BADGE_CLASS`-adjacent existing tokens only: done → `text-emerald-400` / `border-emerald-500/30`; active → `text-amber-400` / `border-amber-500/30` / `bg-amber-500/10`; upcoming → `text-slate-500` / `border-slate-700`; pending → an amber ring on the selected marker. No new token.

## 5. Deviation Register

Judgment calls made here that the roadmap section did **not** already lock. Each is stated with its alternative so this gate can overrule it.

1. **Collapsed = icon-only rail, not fully hidden.** The roadmap says "collapsed to icon-only **or** hidden entirely" and left the choice open; the prompt required picking one and speccing it precisely. Chosen: **icon-only rail at `w-16`, always mounted, all five destinations still clickable**. *Reasoning:* the roadmap's own verification threshold requires the toggle to provably not lose navigation reach, and a fully-hidden sidebar loses reach to four of five routes unless a floating re-open control is also built — extra surface in a phase whose entire point is to remove clutter. *Overrule path:* switch to fully-hidden, and add a floating re-open affordance plus criteria covering its position, its accessible name, and route reachability while hidden (roughly three additional criteria; AC-3, AC-4 and AC-17 would be rewritten).
2. **Collapse state is plain `useState` in `AppInner`, defaulting to expanded, not persisted across reload.** The roadmap requires persistence "across navigation within a session" only, and the prompt explicitly waived reload persistence. *Overrule path:* add a `localStorage` key plus criteria for first-run default, corrupted-value handling, and reload restoration.
3. **Existing in-page back buttons and headings in the five page components stay.** The sidebar arguably makes `EquipmentManager`/`MashProfileManager`/`FermentationProfileManager`/`BatchList`/`BatchDetail`'s own back controls redundant. Removing them would mean dropping `onBack` from five component prop types and repairing roughly forty existing test call sites across four prior-milestone test files — churn on verified M1–M5 tests with no user-visible gain in this phase. *Overrule path:* a follow-up lightweight-task pass (HARD_RULES rule 7 does **not** cover it — it crosses five files) or a small M5.5_P2.
4. **The stepper renders in edit mode only; view mode is unchanged.** The roadmap says the stepper replaces "the `<select>` in `BatchDetail.tsx`'s **edit form**", and the view-mode status badge already communicates current status. *Overrule path:* render a read-only stepper in view mode too, adding roughly two criteria and touching the view-mode branch of `BatchDetail.tsx`.
5. **Transition button copy is taken verbatim from the roadmap and BUG-003's report** ("Advance to Brewing", "Start Fermentation", "Move to Conditioning", "Mark Completed"). No fifth label is invented, because `Planning` is never a forward target.
6. **Pending-transition affordance ("Pending — save to apply" + "Cancel transition") is new and was not specified anywhere.** It exists because the stepper feeds `formData`, not the server: without it, clicking "Advance to Brewing" would visibly change nothing until save, and there would be no way to undo the choice short of Cancel-ing the whole edit. *Overrule path:* make the transition button save immediately (a direct `updateBatch` call from the stepper's handler) — rejected here because it would split the batch page into two independent write paths and contradict §2.5's requirement that `handleSave` stay unchanged.
7. **`TopBar` titles are named strings, one per route** (§2.2), including `Batch` for `batchDetail` rather than the batch name, which is already the page's own `<h1>`-equivalent content. *Overrule path:* pass the batch name up into the top bar, which would require lifting loaded-batch state out of `BatchDetail` into `App` — a real refactor, disproportionate here.
8. **Existing-test repairs are permitted but constrained to query narrowing** (Resolved Ambiguities). This exists so an unavoidable ambiguity from the new `<h1>` is not silently "fixed" by deleting or weakening a prior milestone's assertion. Four test files are listed as *conditionally* modified in §1.2; a file that needed no repair must not appear in AC-33's diff.
9. **Scope guardrail uses a SHA-256 content manifest, not `git diff --name-only`.** Independently checked before writing this: `git log --oneline` returns exactly **one** commit, which predates all of M1–M5's work, so a name-only diff against it is not a meaningful scope signal in this repository. AC-33 specifies the pre/post manifest procedure explicitly rather than leaving the executor with an unsatisfiable criterion.
10. **Playwright is not assumed.** Verified absent from both `package.json` files; prior milestones' Playwright runs were driven by session tooling, not a project dependency. AC-38 and AC-39 therefore require screenshots without naming a capture tool, and no criterion in this spec requires an automated browser run.
