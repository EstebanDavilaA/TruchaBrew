## Phase Summary
Milestone 4s user-visible outcome is: Hit Brew this on a recipe and get a Batch that freezes the recipe exactly as brewed; walk it from Planning into Brewing and record what actually happened — measured pre-boil gravity, mash pH, actual volumes and boil time — and see measured-vs-estimated side by side.

Because M4 is large, this first phase (M4_P1) delivers the **foundation of the Batch entity**: the frozen snapshot, the `Planning → Brewing` pipeline status, the batch list, and the capture of measured values during the Brewing stage. The user explicitly requested in `STATE.json` notes to consider hop-timing semantics (differentiating Boil, Whirlpool, DryHop) that were deferred from M3. We will introduce the `Boil` and `Whirlpool` attributes now, since a brew-day log gives whirlpool time-after-flameout a concrete stage to be logged against. `DryHop` is still deferred to M5 (fermentation).

### Key Behaviors
1. **The snapshot is frozen.** When a batch is created from a recipe, it copies the recipes entire state (ingredients, profiles, stats) into a JSON document or separate snapshot columns. Subsequent edits to the source recipe *must not* retroactively alter the batch.
2. **Status pipeline enforces direction.** `Planning → Brewing` is the only allowed transition in this phase. The status cannot skip or reverse without explicit action.
3. **Hop Use split.** The `HopItem` interface is expanded to differentiate `Boil` and `Whirlpool` attributes, replacing the generic `timeMinutes` for those uses.
4. **Measured Mash Efficiency.** Calculated from the measured pre-boil gravity against the snapshots grain bill, per build-spec §3.9.
5. **No inventory checkoff.** Per the roadmap, inventory deduction in the Planning stage is explicitly out of scope until Milestone 9. Planning is just a read-only brew sheet.

### Resolved Ambiguities (Binding)
- **Hop Timing Split:** 
  - `Boil`: `boilMins` (minutes remaining in the boil).
  - `Whirlpool`: `whirlpoolMins` (minutes after flameout) and `whirlpoolTempC` (temperature of the whirlpool).
  - `DryHop`: **AMENDED 2026-08-07 — see the dedicated bullet below. The pre-amendment text read "Deferred to M5. Remains untouched in this phase," which the migration does not and cannot honour.** The *modelling* work (day-offset from fermentation start, duration in days) is still deferred to M5; the *stored value* is not discarded in the meantime.
  - Existing recipes with `timeMinutes` must be migrated: if `use === Boil`, map to `boilMins`; if `use === Whirlpool`, map to `whirlpoolMins` and assume `whirlpoolTempC` equals the equipment profiles `hopstandTemperatureC`.
- **AMENDED 2026-08-07 — `DryHop`'s `timeMinutes` is preserved verbatim, not dropped.** The pre-amendment spec said two incompatible things about the same rows: Resolved Ambiguities said `DryHop` "remains untouched in this phase", while §2.6 said to remove `timeMinutes` from `HopItem` and `recipe_hops` "after migrating data". For `Boil` and `Whirlpool` those instructions compose. For `DryHop` they do not: the value is copied into neither new column, and then the only column holding it ceases to exist. "Untouched" and "the column was dropped out from under it" are not the same thing, and §2.6's own precondition — *after* migrating the data — is not met for these rows. **Resolution, decided by the user at the halt gate: option (b), defer the retirement to M5.** Option (a) — a `dryHopMinsLegacy` carry-over column, requiring an in-place edit to the already-applied migration `0004` and a dev-DB delete-and-reseed — was drafted, presented, and **overruled. Nothing in this spec implements it, and `dryHopMinsLegacy` must not appear anywhere in the tree.**
  - **`time_minutes` is restored to `recipe_hops` by a new, additive migration `0005`**, as `real` **nullable** — not the pre-M4 `real DEFAULT 0 NOT NULL`. `HopItem` regains `timeMinutes?: number | null`.
  - **The field is scoped down to `DryHop` and means nothing else.** It is meaningful **iff `use === 'DryHop'`**, where it carries the dry-hop duration in minutes exactly as it did before this phase, and is `null` for `Boil`, `FirstWort`, `Whirlpool` and `Aroma`. It is deliberately **not** kept live for all five uses: `Boil`/`FirstWort` now have `boilMins` and `Whirlpool`/`Aroma` have `whirlpoolMins`, so a second field also carrying their timing would be two mutable representations of one quantity with no defined precedence — exactly what M3_P1 deviation 2 rejected `evaporationRate%` for, and what M3_P2's `infuseAmountL` precedence rule exists to prevent. **Narrowing the field's meaning while keeping its name is what makes this a deferral rather than a reopening:** the ambiguity this phase exists to close — one field serving Boil and Whirlpool at once — stays closed, and the only use still reading `timeMinutes` is the one whose replacement model does not exist yet.
  - **It is optional on the domain type**, for the same reason the overruled option (a) made its field optional: a required property would force an edit to every hop object literal in the repo (`seed.ts`, `fixtureAdapter.ts`, `brewingMath.test.ts`, `scaling.test.ts`, both `test/helpers/fixtures.ts`, `HopSection.tsx`) to supply a value that is meaningless for four of the five uses. It rides the domain type at all — rather than living only in the column — because `PUT /api/recipes/:id` rewrites all line-item rows, so a column the row↔domain mapper does not carry is destroyed by the first recipe edit rather than by any migration.
  - **The field is inert and no destination is invented for it.** Nothing reads it: `classifyHopUse('DryHop')` returns `'none'` and `calculateSingleHopIbu` early-returns `0`, so it cannot reach any calculation and no displayed number moves. **No replacement field is introduced before M5** — no `dryHopMinsLegacy`, no `dayOffset`, no `durationDays`. M5 introduces the fermentation timeline that a day-offset is measured *from*, and M5 owns both the real model and the migration that finally drops this column. Storing a day-offset now would be the inert-field anti-pattern P1 deviation 3 rejected; continuing to store the value the user already typed, under the name it already had, is not.
  - **Migration `0004` is byte-unchanged and no database is wiped.** The restoration is a single additive `ALTER TABLE recipe_hops ADD COLUMN time_minutes real;` in a **new** migration `0005`, which applies cleanly both to the developer's existing `apps/api/data/truchabrew.db` and to a fresh chain from `0000`. `meta/_journal.json` gains its `idx: 5` entry — a mechanically-unavoidable `drizzle-kit` output, on the M3_P1 amendment's precedent for this same file — and is otherwise unchanged. **No already-applied migration is edited.** This is the constraint that decided the overrule: option (a) could not be built without editing `0004` in place and forcing a delete-and-reseed of the dev DB, and option (b) costs neither. If execution finds itself editing any file under `apps/api/drizzle/` other than adding `0005` and its snapshot, that is the signal to stop and route back to `/plan`.
  - **Disclosed residual, so AC-10 does not overclaim.** `0004` shipped with its `DROP COLUMN` and is now unmodifiable, so a `DryHop` row's **pre-`0004`** value is not recoverable — not on a database that has already run `0004`, and not on a fresh chain from `0000` either, since `0005` can only re-add an empty column. **What option (b) buys is not historical recovery; that window closed when `0004` shipped.** It buys that from `0005` forward, a `DryHop` hop's `timeMinutes` is a stored, round-tripping field with no invented destination — so no *future* dry-hop timing is destroyed, and M5 inherits one unambiguous source instead of a legacy alias it would first have to migrate off. **In practice the historical loss is nil**: databases are migrated before they are seeded, so a fresh chain has no pre-`0004` dry-hop rows at all, and the only `DryHop` row in the seed corpus is `rh-4` Simcoe at `timeMinutes: 0`. AC-10 is therefore written against what is actually true — correct routing through `0004`, and forward round-tripping from `0005` — and **not** against a "the value survives `0004`" claim that no implementation could satisfy without editing an applied migration.
- **Snapshot Storage:** The recipe snapshot is stored as a single `JSONB` (or SQLite equivalent JSON) column on the `batches` table, containing the fully hydrated `Recipe` object (including profiles and derived stats). This guarantees immutability without needing to clone 4+ line-item tables per batch.
- **AMENDED 2026-08-07 (second amendment) — the derived stats are stored, in their own column. "Including derived stats" is now true rather than aspirational.** The Snapshot Storage bullet above and Key Behavior 1 have both claimed since the first draft that the snapshot carries derived stats. It does not: `Batch.recipeSnapshot` is typed `Recipe`, which structurally cannot hold a `CalculatedStats`, and `BatchDetail.tsx` recomputes them at render time from the frozen recipe. Two independent critic audits traced AC-1 **PARTIAL** for exactly this, and the second proved the mechanism live — mutating the source recipe moved the *recomputed* IBU from 46 to 69 while the stored `recipe_snapshot` stayed byte-identical. **This is the third time the gap has been observed, so it is decided here rather than inherited again. Resolution: persist the stats now (the critic's option (a)); do not defer to M5.**
  - `batches` gains a **nullable** `stats_snapshot` column via a **new, additive migration `0006`** — `ALTER TABLE batches ADD COLUMN stats_snapshot text;`. `Batch` gains `statsSnapshot: CalculatedStats | null`. **`recipeSnapshot` stays typed `Recipe`** and `recipe_snapshot` is byte-unchanged: the stats live in a sibling column, not inside the recipe object, because a `Recipe` that carries its own derived output is no longer a `Recipe` and every existing consumer of that field would have to start ignoring a key.
  - **The stats are computed exactly once, at batch creation**, by the same `calculateRecipeStats` call the app already uses, against the same frozen `Recipe` being snapshotted in the same write. `batchRepository.update()` never touches the column, on the identical rule that already protects `recipe_snapshot`.
  - **Why this is not deferrable to M5.** The exposure is not hypothetical drift; it is **scheduled roadmap work**. `ROADMAP.md`'s **Milestone 7** is, in its own words, "swap the IBU formula from Tinseth to Rager/Garetz/Noonan and ABV from simple to Balling, and see every recipe, batch and calculator in the app respond consistently" — a milestone whose entire purpose is changing the formulas `calculateRecipeStats` runs. Under live recomputation, the day that ships, **every historical batch's estimated OG/IBU/ABV silently rewrites itself**, inside the one entity in this product whose stated reason to exist is measured-versus-estimated comparison. A brew log whose "estimated" column moves after the fact is not a record. **Milestone 5 makes it worse before M7 makes it visible:** M5's hardening scope is "measured OG/FG/ABV/efficiency displayed against the recipe's estimates" and its verification threshold is that after a full restart "the entire history … reads back intact". M5 therefore *builds on* these figures — deferring means M5 inherits a moving baseline and its own threshold becomes unprovable.
  - **Why it is cheap now and expensive later.** Today the change is one additive nullable column, one compute-at-create, and one call site that reads instead of recomputes. Every batch that exists is one row in a pre-release dev database. Deferred to M5, the same change has to be made *plus* a backfill decision for however many real batches the MVP acceptance run has by then produced — and a backfill can only be done by running today's formulas over old snapshots, which is exactly the thing this field exists to stop being authoritative.
  - **The legacy `null` branch is explicit and labelled, not a silent fallback.** `statsSnapshot` is nullable because batches created before `0006` have none, and SQL cannot compute brewing stats to backfill them. When it is `null`, `BatchDetail` recomputes from the frozen recipe **and says so on screen**, so a recomputed figure is never presented as a frozen one. This is the same discipline AC-9 applies to a missing measurement: the honest answer to "we don't have this" is a labelled branch, never an unlabelled number. **No database is wiped and no batch row is deleted to avoid this branch.**
- **Pre-Boil Gravity Calculation:** The formula from §3.9 must use the snapshots fermentables and volume, not the live recipe.
- **AMENDED 2026-08-07 — the "Brew this" entry point is the recipe editor toolbar, and only there.** The pre-amendment spec named no entry point, which is why nothing in the matrix required the create path to be reachable and F-3 went unobserved. Decided, binding, one place:
  - The control lives in the **editor view's header row in `apps/web/src/App.tsx`** — the same row that already holds `Scale Batch` and `Batches` (`App.tsx:391-421`) — labelled **"Brew This"**. It is rendered only in `view === 'editor'`.
  - **Not** the recipe library rows. `RecipeLibrary.tsx` has no knowledge of editor dirty state, and adding the control there would require a new callback prop plus a fresh id round-trip to gain a gate the editor already has in hand. One entry point, one criterion, no second code path to keep consistent.
  - **Gating is `editor.storedId !== null && editor.isDirty === false`.** Both are already returned by `useRecipeEditor` (`useRecipeEditor.ts:273-290`). When either fails the control is `disabled` and carries a `title` naming the reason. This is not cosmetic: the batch snapshot freezes what the **server** holds, so brewing a never-saved or dirty recipe would freeze a state the user never saved — which would make AC-1's guarantee true and useless at the same time.
  - On click it calls `POST /api/batches` with `{ recipeId: editor.storedId }` **through `apps/web/src/api/client.ts`**, not a bare `fetch`, so it inherits `ApiClientError` and structured error parsing like every other mutation in the app. On `201` it takes the created batch's `id`, sets `activeBatchId`, and switches `view` to `'batchDetail'`. On failure it surfaces the server's message and does **not** navigate.

## 2. Transformations & Pure Logic

- **Pure Function Contracts:**
  - `mashEfficiency(actualPreBoilGravityPoints: number, maxPossibleGravityPoints: number): number`
    - Returns the percentage [0, 100].
  - `calculateSingleHopIbu(hop: HopItem, ...)`
    - Must read `boilMins` or `whirlpoolMins` depending on `hop.use`.

- **No-Match / Fallback Contracts — AMENDED 2026-08-07.** The pre-amendment text read: *"If a batch has no measured pre-boil gravity, `mashEfficiency` is not calculated and returns `null`."* That sentence conflates two contracts at two different layers, which is why AC-6 was tested against a property it does not describe. They are now separated, and **neither one is optional**:
  - **Calc layer.** `mashEfficiency`'s signature is `(actualPreBoilGravityPoints: number, maxPossibleGravityPoints: number) => number | null`. It returns `null` **iff `maxPossibleGravityPoints <= 0`** — a degenerate *denominator*, which is the only degenerate condition a function taking two numbers can express. Otherwise it returns `(actual / max) * 100`, unclamped. It never returns `NaN` or `Infinity`. It knows nothing about batches, measurements or their absence, and it must not be given a sentinel number standing in for a missing measurement.
  - **UI layer.** "No measured pre-boil gravity" is a **caller-side** condition and is the caller's responsibility. When `batch.measuredPreBoilGravity` is `null` or absent, the efficiency display is **suppressed** — `mashEfficiency` is not called at all, and no placeholder (`0`, `—`, `NaN`, `0.0 %`) is rendered in a slot the user could read as a measurement. The check is on `!== null`, never on falsiness alone, for the same reason M3_P2 bound `resolveSpargeTemperatureC` to `!== null`: a legitimate stored `0` is not absence. A `null` returned by the calc layer is likewise rendered as suppression, never as a number.

- **Stateful Integration Contract:**
  - The UI must display the recipes estimated pre-boil gravity next to an input field for the measured pre-boil gravity.
  - **Added 2026-08-07 (second amendment).** The estimated figures shown on a batch are **read from `batch.statsSnapshot`**, never recomputed, whenever it is non-`null`. When it is `null` — a batch created before migration `0006`, and only then — the view recomputes from the frozen `recipeSnapshot` **and labels the figures as recomputed rather than stored**. A recomputed figure must never occupy the same unlabelled slot as a stored one. The measured column is unaffected: it still comes from the batch's own measured fields, and AC-9's suppression rule governs it.
  - **Added 2026-08-07.** The "Brew This" control is a stateful integration, not pure logic, and its full contract — placement, gating on `storedId`/`isDirty`, the `POST` through `client.ts`, the navigation on `201`, the no-navigation-on-failure rule — is in the entry-point Resolved Ambiguity above and is pinned by AC-8.

- **Refactoring & Legacy Cleanup:**
  - Remove `timeMinutes` from `HopItem` type and `recipe_hops` schema after migrating data.
  - **AMENDED 2026-08-07 — "after migrating data" is a precondition, and for `DryHop` it was not met, so the retirement is partial.** `timeMinutes` is retired **as a Boil/Whirlpool timing field, and only as that**: `Boil`/`FirstWort` read `boilMins`, `Whirlpool`/`Aroma` read `whirlpoolMins` (+ `whirlpoolTempC`), and no code path reads `timeMinutes` for any of those four uses ever again. It is **not** removed from `HopItem` or from `recipe_hops` in this phase — it is narrowed to a `DryHop`-only field, restored by migration `0005`, and its removal is deferred to **M5**, which owns DryHop's real day-offset/duration model and the migration that finally drops the column. The pre-amendment instruction to "remove `timeMinutes` from `HopItem` type and `recipe_hops` schema" therefore stands **for the four Boil/Whirlpool-class uses and is deferred for `DryHop`**. `MiscItem.timeMinutes` is **not** in scope for this cleanup and is not touched.
