> **Milestone 5.5, Phase 2.** Second post-MVP phase. Pure UX rework of already-shipped surfaces.
> Closes **BUG-004** (Equipment / Mash / Fermentation Profile create-edit renders as a centered modal dialog instead of the full-page + `TopBar`-contextual-actions pattern established by M5.5_P1).
> **Zero** API, schema, migration, `packages/calculations` or `packages/shared-types` work. Zero new npm dependency, zero new Tailwind or theme token. If execution discovers it needs any of those, that is a **deviation** to raise at a halt, not a change to make.

## Phase Summary

M5.5_P1 established the application shell: a persistent `Sidebar` on every route, and a `TopBar` carrying the current page's title plus that page's contextual actions in its `children` slot. The Recipe Editor route and the Batch Detail route both use it — the editor's Scale Batch / Brew This / SaveBar controls all live in the top bar, and the page body owns the whole content area under the sidebar.

The three profile editors did not get that treatment. `EquipmentForm.tsx`, `MashProfileForm.tsx` and `FermentationProfileForm.tsx` each render as `fixed inset-0` + `backdrop-blur-sm` overlay dialogs with their own inline `Cancel` / `Save …` footer, floating above a blurred, unusable page. Creating or editing a profile therefore feels like a different application from creating or editing a recipe.

This phase converts all three to the full-page pattern:

- Each form **takes over the main content area** under the persistent sidebar. No `fixed`, no `inset-0`, no backdrop, no `z-50` overlay, no `max-h-[90vh]` scroll box.
- **Save and Cancel move into the `TopBar`'s `children` slot** as contextual actions, exactly as `SaveBar` / Scale Batch / Brew This do on the editor route. The inline footer is deleted.
- The **page title becomes the form's title** — `New Equipment Profile`, `Edit All-Grain 20L System`, and so on — rendered as the route's single `<h1>` by `TopBar`, replacing the modal's `<h3>`.
- The **sidebar stays visible, unblurred and fully clickable** the whole time.

**The forms' field sets, validation rules, submit payloads, save-state machine, error banners and `onSaved` / `onCancel` callbacks are unchanged.** This is a container and layout change only. That is the load-bearing claim of the whole phase, and §3 verifies it by requiring named existing test blocks to keep passing **unmodified**, not by asserting "nothing should change".

### Key Behaviors

1. Opening create or edit for any of the three profile types replaces the manager's list with a full-page form under the sidebar. Nothing is rendered `fixed`, nothing is blurred, nothing overlays.
2. While a form is open, the `TopBar` carries the form's title, a leading back/cancel control, and exactly two contextual action buttons: `Cancel` and the entity's Save button.
3. While a form is open, the manager's list, its empty state, its error panel and its "New …" button are **not** rendered. The form is the page.
4. Cancel returns to the list with the list's own `TopBar` title restored. Save calls the same API client function with the same payload as before, then returns to the list on success and stays on the form with the user's edits and an error banner on failure.
5. The sidebar is present, expanded/collapsed exactly as the user left it, and every destination is clickable while a form is open.
6. Every route continues to render **exactly one** `<h1>` (M5.5_P1's AC-14 invariant), including while a form is open.

### Resolved Ambiguities (Binding)

- **The form is an in-place full-page swap inside the manager component, NOT a new `View` union member.** `App.tsx`'s `type View` gains no members; `Sidebar.tsx`'s `ActiveView` union and `activeDestinationFor` are untouched; the `formTarget` state stays exactly where it is today, in `EquipmentManager` / `MashProfileManager` / `FermentationProfileManager`. **Justification (the "smaller, more consistent change" the phase was asked to pick):** promoting the forms to App-level views would require three new `View` members, three new `formTarget` state fields plus their setters in an already-651-line `AppInner`, six new handlers, rewiring `onCreated`/`onUpdated`/`onDeleted` through two levels, and a matching widening of `Sidebar`'s total `ActiveView` mapping — for zero user-visible difference, since there is no URL routing in this application at all (navigation is `useState<View>`, so "its own route" is not a thing that exists to be gained). The in-place swap touches three managers, three forms, and three lines of `App.tsx`. Recorded as **deviation-register entry 1**.
- **`TopBar` rendering for these three routes moves from `App.tsx` into the manager component.** This is the mechanism that lets Save/Cancel reach `TopBar`'s `children` slot without portals, context, or lifted form state. `App.tsx`'s `equipment` / `mashProfiles` / `fermentationProfiles` branches each **delete their one `<TopBar title="…" />` line** and nothing else; the manager renders `<TopBar>` itself in list mode, and the **form** renders `<TopBar>` itself in form mode. React portals, a new context provider, a DOM-id slot, and a `document.getElementById` lookup are all **explicitly non-compliant** implementations of this requirement — each of them would make the manager's standalone unit tests (which render the manager with no `App` above it) depend on ambient DOM that does not exist there. Recorded as **deviation-register entry 2**.
- **Exactly one `TopBar` renders per route at any time.** In list mode the manager renders it; in form mode the form renders it and the manager renders no other. Never both, never neither. This is what preserves M5.5_P1's AC-14 one-`<h1>`-per-route invariant.
- **`TopBar`'s existing contract is reused verbatim and `TopBar.tsx` is not modified.** Its `title` prop is optional (two routes omit it deliberately); this phase always passes a title, so `title` is always a `string` at every new call site introduced here. `leading` and `children` are used as-is. No new prop is added to `TopBarProps`.
- **Route titles in list mode are byte-identical to what `App.tsx` passes today**: `"Equipment Profiles"`, `"Mash Schedules"`, `"Fermentation Schedules"`. Moving the `TopBar` call into the manager must not change the string, or M5.5_P1's `ROUTE_H1` table in `App.test.tsx` breaks.
- **Form titles are byte-identical to the modal `<h3>` text they replace**: create → `"New Equipment Profile"` / `"New Mash Schedule"` / `"New Fermentation Schedule"`; edit → `` `Edit ${initialProfile.name}` `` in all three. The heading **level** changes (`<h3>` inside the dialog → `<h1>` owned by `TopBar`), the text does not.
- **Save button labels are byte-identical**: `"Save Profile"` (equipment), `"Save Schedule"` (mash and fermentation), with the same `Loader2`-spinner / `"Saving…"` swap while `saveState === 'saving'` and the same `disabled={saveState === 'saving' || hasErrors}` predicate. Several existing tests match `/save profile/i` and assert `toBeDisabled()`; those assertions must keep passing against the button in its new location.
- **The leading control keeps the accessible name `"Cancel"`.** Today each form header has an `X` icon button with `title="Cancel"` **and** a text `Cancel` button in the footer — two controls whose accessible name is "Cancel". The converted form keeps exactly two: `TopBar`'s `leading` becomes an `ArrowLeft` icon button with `title="Cancel"` and `aria-label="Cancel"` calling `onCancel`, and the text `Cancel` button moves into `children`. Rationale: any existing query for a "Cancel"-named button is ambiguous today and must remain **exactly as ambiguous** after the change — neither newly-resolving nor newly-throwing — so that no existing test's outcome silently flips. Using `ArrowLeft` instead of `X` matches the editor route's leading control; the icon identity is not an acceptance criterion.
- **The manager's in-page header card is deleted; its two controls are re-homed, not dropped.** Today each manager renders a `bg-slate-900 … rounded-xl` card containing a back-arrow button (`onClick={onBack}`), an `<h2>` with the route title, and the `New Profile` / `New Schedule` button. After this phase: the back arrow becomes `TopBar`'s `leading` (still `onClick={onBack}`, still `title="Back"`), the `<h2>` is deleted because `TopBar`'s `<h1>` now carries that text, and the `New …` button becomes `TopBar`'s `children` — **retaining its `data-testid` verbatim** (`equipment-new-profile`, `mash-new-profile`, `fermentation-new-profile`). This closes, for these three routes only, the redundancy M5.5_P1 deliberately deferred as its own deviation-register entry 3. Recorded as **deviation-register entry 3**.
- **The `onBack` prop is retained on all three managers.** It is **not** removed and its call sites are not touched. `App.tsx`'s `leaveEquipment` / `leaveMashProfiles` / `leaveFermentationProfiles` (which return the user to the open recipe editor when `editor.recipe` is non-null, and to the library otherwise) survive unchanged — that return-to-editor path has no sidebar equivalent, and removing the prop would churn 18 existing `onBack={noop}` / `onBack={vi.fn()}` render call sites across two test files for no gain. Recorded as **deviation-register entry 4**.
- **No unsaved-changes guard is added, and none exists today — this is explicitly out of scope.** Neither the three forms nor the three manager routes have ever had a dirty-check. Today, clicking a sidebar destination while a modal is open unmounts the manager and discards the edits silently; after this phase the identical thing happens with a full-page form. The behavior is therefore **preserved, not regressed**, and AC-24 asserts that no `window.confirm` is introduced on these paths. Reasons for scoping it out: (a) it is new user-visible behavior, which makes it a separate slice, not a container refactor; (b) doing it properly needs a dirty predicate over each form's raw string state, which is real logic and belongs in a spec that can pin its edge cases (is `20` vs `20.0` dirty? is an untouched create form with default values dirty?); (c) M5.5_P1's existing editor guard (`confirmLeaveEditorIfDirty`) is scoped to the Recipes destination only, and extending that asymmetry is a design decision, not an implementation detail. Recorded as **deviation-register entry 5** with a recommendation to raise it at `/steer` as candidate M5.5_P3 or a BUGS.md entry.
- **`Cancel` while `saveState === 'saving'` stays disabled**, exactly as the current footer button is (`disabled={saveState === 'saving'}`). The leading `ArrowLeft` control gets the **same** `disabled={saveState === 'saving'}` guard — today the `X` control had no such guard, which is a latent inconsistency this conversion closes; it is a strictly-narrowing change to a control that was already there.
- **No visual/theme tokens are introduced.** Every class used must already appear somewhere in `apps/web/src/`. Content width for the converted forms is the existing `max-w-4xl mx-auto px-4 sm:px-6 lg:px-8 pt-6` wrapper the managers already use (the modals' `max-w-2xl` / `max-w-3xl` inner boxes are deleted along with the overlay). No `dark:` variant, no new colour ramp, no arbitrary-value class beyond ones already present in the file being edited.
- **`saveState`, `saveError`, `hasErrors`, `handleSubmit`, every `validate*` helper, every `RawValues` / `RawMashStepRow` / `RawFermentationStepRow` shape, `DEFAULT_NEW_PROFILE`, `NUMERIC_FIELDS`, `toRawValues`, `toRawSteps`, `blankStepRow`, `addStep` / `removeStep` / `moveStep`, `MASH_STEP_TYPES`, `FERMENTATION_STEP_TYPES` and both discriminated-union prop types are byte-identical after this phase.** The only permitted edits inside the three form files are to the returned JSX and to the `lucide-react` import list.
- **Degenerate/empty inputs behave as today.** A create form opens with zero steps (mash/fermentation) and renders the existing "No steps yet" note; a manager with zero profiles and no load error renders the existing empty state **in list mode only**. Neither state has any interaction with the container change, and neither may be altered.

## 2. Component Contracts

### 2.1 Pure-logic contracts

**None.** This phase adds no pure function, no derived-state helper, and no calculation. Every existing pure helper listed in §1.4 keeps its current signature and behavior byte-for-byte. There is consequently no no-match / empty-input return value to define at the pure-logic layer — the corresponding degenerate cases are all stateful render cases and are pinned in §2.2–§2.3 instead.

### 2.2 Converted form — shared contract for all three forms

Applies identically to `EquipmentForm`, `MashProfileForm`, `FermentationProfileForm`. Per-entity strings are tabulated below.

**Props:** unchanged discriminated union — `{ mode: 'create'; initialProfile?: undefined; onSaved; onCancel }` | `{ mode: 'edit'; initialProfile: <Entity>; onSaved; onCancel }`. No prop added, removed or made optional.

**Render structure (in order, as the component's single fragment/root):**

1. `<TopBar title={formTitle} leading={leadingControl}>` `{cancelButton}{saveButton}` `</TopBar>`
   - `formTitle`: `mode === 'create' ? CREATE_TITLE : \`Edit ${initialProfile.name}\`` — a `string`, never `undefined`, so `TopBar` always renders its `<h1>` here.
   - `leadingControl`: a `<button type="button">` rendering `ArrowLeft`, with `title="Cancel"` **and** `aria-label="Cancel"`, `onClick={onCancel}`, `disabled={saveState === 'saving'}`.
   - `cancelButton`: `<button type="button" onClick={onCancel} disabled={saveState === 'saving'}>Cancel</button>` — the existing footer button, moved, text unchanged.
   - `saveButton`: `<button type="submit" form={FORM_ID} disabled={saveState === 'saving' || hasErrors}>` with the existing `Loader2`-spinner / `Save` icon swap and the existing `"Saving…"` / `SAVE_LABEL` text swap. Because the button now lives outside the `<form>` element's subtree, it **must** carry the native `form={FORM_ID}` attribute and the `<form>` element **must** carry the matching `id={FORM_ID}`. This is the only supported submit-association mechanism for this phase — no `useRef` + `requestSubmit()`, no lifted callback, no duplicated submit handler.
2. The page body: the existing content wrapper `<div className="max-w-4xl mx-auto px-4 sm:px-6 lg:px-8 pt-6">` containing `<form id={FORM_ID} onSubmit={handleSubmit}>` with **every existing field block, step row, hint, inline field error and the `saveState === 'error'` banner in their current order and with their current markup**, minus the deleted header row and footer.

**No element in the returned tree may carry any of:** `fixed`, `inset-0`, `backdrop-blur`, `backdrop-blur-sm`, `z-50`, `max-h-[90vh]`. This is checkable by string search over the file and by class inspection over the rendered DOM; both are used in §3.

**Per-entity strings and ids (binding):**

| Component | `CREATE_TITLE` | `SAVE_LABEL` | `FORM_ID` |
|-----------|----------------|--------------|-----------|
| `EquipmentForm` | `New Equipment Profile` | `Save Profile` | `equipment-profile-form` |
| `MashProfileForm` | `New Mash Schedule` | `Save Schedule` | `mash-profile-form` |
| `FermentationProfileForm` | `New Fermentation Schedule` | `Save Schedule` | `fermentation-profile-form` |

Edit-mode title is `` `Edit ${initialProfile.name}` `` in all three.

**Unchanged behavior (must remain true, asserted via preserved tests):** `handleSubmit` early-returns on `hasErrors || saveState === 'saving'`; the payload object is constructed field-for-field as it is today; `create*` is called in create mode and `update*(initialProfile.id, payload)` in edit mode; on success `setSaveState('idle')` then `onSaved(result)`; on failure `setSaveState('error')` + `setSaveError(...)` and **the component stays mounted with every raw value intact**.

### 2.3 Stateful integration contract — the three managers

`formTarget: FormTarget` state, its `useState` initialiser, and both setter call sites (`setFormTarget({ mode: 'create' })`, `setFormTarget({ mode: 'edit', profile })`, `setFormTarget(null)`) are **unchanged**. What changes is only what the component returns for each value of it.

**Branching contract (binding — the caller must branch, not overlay):**

- `formTarget?.mode === 'create'` → return **only** the form usage with `key="create"`, `mode="create"`, `onSaved={(created) => { onCreated(created); setFormTarget(null); }}`, `onCancel={() => setFormTarget(null)}`. Verbatim the props passed today.
- `formTarget?.mode === 'edit'` → return **only** the form usage with `` key={`edit-${formTarget.profile.id}`} ``, `mode="edit"`, `initialProfile={formTarget.profile}`, `onSaved={(updated) => { onUpdated(updated); setFormTarget(null); }}`, `onCancel={() => setFormTarget(null)}`. Verbatim.
- `formTarget === null` → return list mode: the manager's own `<TopBar title={ROUTE_TITLE} leading={backControl}>{newButton}</TopBar>` followed by the existing content wrapper with the load-error panel / empty state / profile rows exactly as they render today.

In form mode the manager renders **no** `TopBar` of its own, **no** list, **no** empty state, **no** load-error panel and **no** "New …" button. In list mode it renders **no** form. There is no state in which both a list and a form are mounted — that is the concrete difference from the modal implementation and AC-7/AC-8 test it directly.

**List-mode `TopBar` slots (binding):**

| Manager | `ROUTE_TITLE` | `leading` | `children` |
|---------|---------------|-----------|------------|
| `EquipmentManager` | `Equipment Profiles` | `ArrowLeft` button, `title="Back"`, `onClick={onBack}` | `New Profile` button, `data-testid="equipment-new-profile"`, `onClick={() => setFormTarget({ mode: 'create' })}` |
| `MashProfileManager` | `Mash Schedules` | `ArrowLeft` button, `title="Back"`, `onClick={onBack}` | `New Schedule` button, `data-testid="mash-new-profile"` |
| `FermentationProfileManager` | `Fermentation Schedules` | `ArrowLeft` button, `title="Back"`, `onClick={onBack}` | `New Schedule` button, `data-testid="fermentation-new-profile"` |

**Degenerate cases:** zero profiles + no load error → list mode still renders its `TopBar` **and** the existing empty-state card (never a form, never a fabricated placeholder profile). Non-null `loadError` → list mode renders its `TopBar`, the existing error panel with `Retry`, and **not** the empty state; the `New …` button remains present and clickable in the `TopBar` (this matches today's behavior, where the header card's New button is rendered regardless of `loadError`). Neither degenerate case may be changed by this phase.

### 2.4 Stateful integration contract — `App.tsx`

The three route branches keep their shell wrapper (`<div className="min-h-screen bg-slate-950 … flex">`, `<Sidebar … />`, `<div className="flex-1 min-w-0 pb-16">`) and their manager usage with every prop unchanged. They simply no longer render a `TopBar`; the manager subtree does. `sidebarCollapsed` continues to live in `AppInner` above the route switch, so the sidebar's collapse state is unaffected by opening or closing a form.

## 4. Verification Threshold

This phase is complete when **all** of the following hold, each by an objective check:

1. AC-1 through AC-33 all trace **YES** under an independent critic audit that re-derives them against the code rather than reading the executor's test output.
2. All four Layer-1 gates (AC-28..AC-31) exit 0, each reported with its actual exit code.
3. The named existing test blocks in AC-11, AC-12 and AC-19 pass with their assertions **byte-unchanged**, verified by diffing those blocks between the pre- and post-execution copies of the three test files — this is the primary evidence that field sets, validation and submit payloads are unchanged.
4. The AC-25 manifest diff contains exactly the eleven expected paths.
5. Layer 3 regression: the full `npm test` run is green including M1's calculation fixtures, M2's persistence/scaling suites, M3's equipment and schedule suites, M4/M5's batch suites, and M5.5_P1's `Sidebar`/`TopBar`/`BatchStepper` suites.
6. Three manual screenshots present and non-stale.

**Explicitly NOT part of this threshold:** any unsaved-changes guard, any change to what the forms submit, any URL/routing behavior, any restyling of the form fields themselves, and M5.5_P1's own outstanding Layer 2/Layer 3 verification (which remains owed against `M5.5_P1_feature_spec.md` separately).

## 5. Deviation Register

Each entry states the decision, the rejected alternative, and what overruling it at the halt gate would cost.

1. **Forms stay nested in their managers; no new `View` union members.** Rejected alternative: promote each form to an App-level route (`'equipmentForm' | 'mashProfileForm' | 'fermentationProfileForm'`), lift `formTarget` into `AppInner`, widen `Sidebar`'s `ActiveView` mapping. Cost of overruling: `App.tsx` grows three state fields, six handlers and three route branches; `Sidebar.tsx` leaves §1.3's untouched list; the diff roughly triples; and the Save button then needs form-internal validity state lifted or portalled anyway. Benefit foregone: none observable, because the app has no URL routing to gain.
2. **`TopBar` rendering moves from `App.tsx` into the manager/form subtree.** Rejected alternatives: a React context slot or a `createPortal` into a DOM node owned by `TopBar`. Cost of overruling: the three managers' standalone unit tests (which render with no `App` above them) would need a provider wrapper or a fabricated portal host, breaking the "existing blocks pass unmodified" evidence that AC-11/AC-12 rest on.
3. **The managers' in-page header card is deleted**, with its back arrow re-homed to `TopBar.leading` and its `New …` button to `TopBar.children`. This closes, for these three routes only, the redundancy M5.5_P1 deliberately deferred (its deviation 3). Rejected alternative: keep the card and let the route title appear twice (`<h1>` in the bar, `<h2>` in the card). Cost of overruling: visible duplicate titles and a second back control on three routes; no test breaks either way.
4. **`onBack` is retained on all three managers** and `App.tsx`'s three `leaveX` handlers survive. Rejected alternative: delete the prop now that the sidebar exists. Cost of overruling: 18 existing `onBack={…}` render call sites across two test files must change, and the "return to the recipe editor I came from" path is lost with no sidebar equivalent.
5. **No unsaved-changes guard — explicitly out of scope**, with behavior preserved exactly as today (edits are discarded silently on navigate-away, as they already are behind the modal). Rejected alternative: add a dirty-check + `window.confirm` to the three forms in this phase. Cost of overruling: new user-visible behavior inside a container-only refactor, plus a dirty predicate over raw string state whose edge cases (`20` vs `20.0`, an untouched create form at defaults) this spec does not pin. **Recommendation: raise at `/steer` as a candidate M5.5_P3 or a fresh BUGS.md entry**, covering the recipe editor's existing asymmetric guard at the same time.
6. **Submit association uses the native `form={FORM_ID}` attribute** rather than a ref + `requestSubmit()` or a lifted submit callback. Rejected alternatives both require touching `handleSubmit` or adding state, which §1.2 forbids. Cost of overruling: the "form file changes are JSX-only" guarantee is lost, and with it the strength of AC-13's payload-preservation argument.
7. **A new `FermentationProfileManager.test.tsx` is added** because that manager has no test file at all today. Rejected alternative: leave the third conversion covered only by the `App.test.tsx` integration blocks. Cost of overruling: AC-17's create/save-failure coverage for fermentation profiles disappears, leaving one of the three converted forms with no component-level test.
8. **AC-25 uses a SHA-256 content manifest instead of `git diff --name-only`.** The repo's single commit predates the monorepo restructure, so a git-diff-based guardrail would report hundreds of pre-existing paths and be unverifiable in practice. Cost of overruling: the scope guardrail becomes unsatisfiable as written — the exact failure mode this framework has already hit repeatedly.
